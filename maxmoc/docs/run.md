# Как запускать max-mock

Инструкция для трёх ролей: разработчика на своей машине, администратора
стенда в закрытом контуре и тестировщика, который играет роль клиента.

---

## 1. Быстрый старт на своей машине

Нужен только Go ≥ 1.22 — ни npm, ни Docker, ни системного SQLite.

```bash
cd maxmoc
make run
```

Увидите:

```
max-mock: конфига config.yaml нет, запускаюсь на значениях по умолчанию
max-mock: контракт 0.0.33, слушаю :8080
max-mock: админка http://localhost:8080/mock, публичный адрес http://localhost:8080
```

Проверка живости — `curl http://localhost:8080/healthz` должен ответить `ok`.

Остановка — `Ctrl+C`. Мок дожидается доставки событий, уже стоящих в очереди,
и только потом завершается.

### Что появляется на диске

| Файл | Что это |
|---|---|
| `max-mock` | собранный бинарник |
| `max-mock.db` (+ `-wal`, `-shm`) | состояние: боты и их токены, диалоги, сообщения, подписки, журналы |
| `blobs/` | загруженные файлы |

Всё переживает перезапуск. Проверить, какой именно файл открыт, можно по
первым строкам лога — путь печатается развёрнутым, вместе с числом найденных
ботов:

```
max-mock: состояние — база /Users/aay/.../maxmoc/max-mock.db, файлы /Users/aay/.../maxmoc/blobs (ботов: 3)
```

> **Если боты «пропали» после перезапуска** — почти всегда открыт другой файл
> базы. Путь `max-mock.db` по умолчанию **относительный**: запуск из другого
> каталога молча создаёт новую пустую базу. Сравните путь в логе с тем, где
> лежат ваши данные, либо задайте абсолютный путь через `db_path` в конфиге
> или `MAXMOCK_DB_PATH`.

Сброс состояния — отдельная цель с подтверждением, потому что вместе с базой
теряются токены ботов и стенды придётся перенастраивать:

```bash
make reset CONFIRM=yes     # удалить боты, диалоги, файлы
make clean                 # только собранные бинарники, состояние не трогает
```

## 2. Первые пять минут: от пустого мока до работающего диалога

### Шаг 1. Зарегистрировать бота

Откройте **http://localhost:8080/mock** — это админка. Заполните имя бота
(например, «Бот поддержки») и нажмите «Зарегистрировать».

В таблице появится строка с `access_token` — нажмите на него, чтобы
скопировать. Это тот самый токен, который КЦ передаёт в запросах.

То же самое из терминала:

```bash
curl -s -X POST http://localhost:8080/mock/api/bots \
  -H 'Content-Type: application/json' \
  -d '{"name":"Бот поддержки","username":"support_bot"}' | jq .
```

### Шаг 2. Направить приложение на мок

В настройках интеграции замените базовый адрес:

```
было:  https://platform-api2.max.ru
стало: http://<адрес-мока>:8080
```

Если мок поднят по HTTPS (см. «Запуск по HTTPS» ниже), схема остаётся
`https://` — меняется только имя хоста.

Больше ничего менять не нужно: пути (`/me`, `/messages`, `/subscriptions`,
`/answers`, `/uploads`, `/me/commands`) и авторизация совпадают с
документацией Max — токен уходит голым в заголовке `Authorization`, без схемы
`Bearer` и без `?access_token=` в query (живой Max их тоже не принимает).

Проверить связь:

```bash
curl -s http://localhost:8080/me -H "Authorization: <token>" | jq .
```

### Шаг 3. Подписать стенд на события

Это делает само приложение при старте — обычным вызовом контракта:

```bash
curl -s -X POST http://localhost:8080/subscriptions \
  -H "Authorization: <token>" -H 'Content-Type: application/json' \
  -d '{"url":"http://<адрес-стенда>/max/v1.0/webhooks/<integrationId>","secret":"stand-secret-123"}' | jq .
```

Мок принимает `http://` (контракт Max требует `https://`, но в закрытом
контуре его обычно нет) и помечает это в поле `message` ответа.

Если задан `secret`, каждый webhook-POST придёт с заголовком
`X-Max-Bot-Api-Secret` — проверяйте его на стенде.

> **Ограничение контракта на секрет:** от 5 до 256 символов, только латиница,
> цифры, `_` и `-` (`^[a-zA-Z0-9_-]{5,256}$`). Кириллица и пробелы не
> проходят — мок ответит `400` с кодом `mock.validation`, ровно как это
> сделал бы реальный Max.

### Шаг 4. Поговорить с ботом

Откройте **http://localhost:8080/mock/chat/{botId}** — ссылка «Открыть чат»
в админке ведёт туда же. Это закладка тестировщика: у каждого свой бот, друг
другу не мешают.

1. Кнопка **«+»** слева — создать клиента (виртуального пользователя Max).
   Форма спрашивает имя, фамилию, username, телефон, координаты и `user_id`;
   всё кроме имени необязательно — см. «Карточка клиента» ниже.
2. Кнопка **«Начать»/«Остановить»** — как в настоящем мессенджере; уходит
   `bot_started` или `bot_stopped`. Кнопка не одноразовая: после нажатия
   подпись меняется на противоположную и берётся из ответа сервера, а не
   гаснет, — так же можно проверить и повторный старт после остановки.
3. Над полем ввода — полоса чипов с командами бота (`/start`, `/operator`…),
   если бот вызвал `PATCH /me/commands`; нет команд — нет и полосы. Клик по
   чипу отправляет обычное сообщение с текстом команды (`message_created`),
   а не `bot_started` — это разные события, и подменять одно другим нельзя.
4. Поле внизу — написать боту; уходит `message_created`.
5. Ответ КЦ появится в чате **сам**, без перезагрузки страницы.
6. Кнопки в сообщениях бота кликабельны — см. «Кнопки» ниже.
7. Скрепка — отправить файл, **👤** — свой контакт, **📍** — геопозицию.
   Свои сообщения можно править и удалять.
8. Вкладка **«События»** — разговор мока и бота парами «запрос → ответ»: что
   ушло на стенд и чем стенд ответил, что прислал бот и что ответил мок. См.
   «Если что-то не работает» ниже про карточку без кода доставки.

### Карточка клиента

Заполнять её стоит целиком: половина сценариев КЦ без этого непроверяема.

| Поле | Куда доезжает до бота |
|---|---|
| Имя, фамилия, username | в каждое событие — поле `sender` или `user` |
| Телефон | **только** вложением `contact` |
| Координаты | **только** вложением `location` |
| `user_id` | в каждое событие; задаётся вручную |

Телефона и координат в схеме пользователя Max нет вовсе — поэтому кнопка
«поделиться контактом» и есть тот механизм, которым КЦ получает номер и
связывает его со своей записью абонента: в одном вложении приезжают и
телефон, и `user_id`.

**`user_id` можно задать явно** — тогда на моке появится ровно тот абонент,
который заведён в тестовых данных КЦ, и сверять события можно по
идентификатору, а не по имени. Занятый идентификатор мок отвергает
(`409 mock.conflict`), а не подменяет молча.

Клиент без телефона на «поделиться контактом» ответит отказом: контакт без
номера бессмыслен, и лучше увидеть это в чате, чем разбираться со стороны КЦ,
почему пришло пустое вложение.

### Кнопки

| Тип кнопки (inline / reply) | Что происходит при нажатии |
|---|---|
| `request_contact` / `user_contact` | боту уходит сообщение с вложением `contact`: телефон в VCARD и `user_id` в `max_info` |
| `request_geo_location` / `user_geo_location` | сообщение с вложением `location`; при `quick: true` — сразу, иначе чат спросит координаты (по умолчанию из карточки) |
| `message` | обычное сообщение с текстом кнопки |
| `clipboard` | текст копируется в буфер обмена, боту не уходит ничего |
| `callback` | `message_callback` с `payload` |
| `link` | открывается адрес |
| `chat`, `open_app` | кнопка неактивна: первая требует группы `/chats`, вторая — мини-приложения, обе вне объёма мока |

> **Нажатие `message`-кнопки неотличимо от набранного вручную текста.**
> Контракт не предусматривает поля, в котором до бота доехал бы «токен
> кнопки», — даже там, где он объявлен (reply-клавиатура). Нужна
> различимость — используйте `callback` с `payload`.

Вкладки **«Журнал»** и **«Доставки»** — главный инструмент отладки: там видны
все входящие вызовы Bot API с телами и статусами и все попытки доставки
webhook-ов на стенд. В чате журнал всегда показан **в разрезе этого бота**.
Вкладка **«События»** показывает то же самое в разрезе **текущего диалога** и
парами: каждая карточка — один обмен, запрос одной стороны и ответ другой.
Искать причину и следствие по двум разным вкладкам вручную не нужно. Вызовов
бота вне диалога (`GET /me`, `PATCH /me/commands`, подписки, загрузки) там нет
— они относятся ко всему боту, и смотреть на них надо в «Журнале».

### Журнал в админке

Карточка «Журнал запросов Bot API» на `/mock` показывает вызовы **всех**
ботов сразу; каждая запись подписана именем бота, а вызовы без токена
помечены «без авторизации». Выпадающий список **«Бот»** сужает журнал до
одного бота — то же, что вкладка «Журнал» в его чате, но не выходя из
админки. Рядом список **«Показывать»** задаёт глубину (50 / 100 / 500 записей).

Для каждой записи видны обе стороны обмена: **запрос** — что прислал КЦ,
**ответ** — что вернул мок. Журнал обновляется живьём, выбранный фильтр при
этом сохраняется.

### Проверить всё разом, не открывая браузер

```bash
make smoke
```

Скрипт поднимает временный стенд-приёмник и проходит полный круг: бот →
подписка → «Начать» → сообщение → кнопки → ответ на нажатие → загрузка файла
→ правка → удаление. В конце печатает список полученных событий. Нужны
`curl`, `python3` и `jq`.

## 3. Запуск в закрытом контуре

### Сборка

Собирайте **на машине с интернетом**, переносите один файл:

```bash
make release                      # linux/amd64 по умолчанию
make release GOARCH=arm64         # если контур на ARM
```

Получится `max-mock-linux-amd64` (~13 МБ): статический бинарник без cgo и
внешних зависимостей. Веб-интерфейс и оба OpenAPI-контракта вшиты внутрь —
рядом класть нечего.

### Конфигурация

Скопируйте `config.example.yaml` в `config.yaml` и поправьте:

```yaml
listen: ":8080"

# КРИТИЧЕСКИ ВАЖНО: адрес, по которому мок виден СО СТЕНДОВ КЦ.
# Он подставляется в upload-адреса и ссылки на вложения. Если оставить
# localhost, стенд не сможет забрать файлы.
public_base_url: "http://max-mock.stand.local:8080"

db_path: "/var/lib/max-mock/max-mock.db"
blob_dir: "/var/lib/max-mock/blobs"

log_retention_days: 14      # чистка журналов; 0 — не чистить
validate_responses: true    # проверять свои ответы по контракту

log:
  format: "text"            # text | json
  level: "info"             # debug | info | warn | error
  body_limit: 4096          # байт тела в строке лога; 0 — не печатать тела

webhook:
  timeout_sec: 10
  retries: 2
  backoff_sec: [1, 5]
```

Запуск:

```bash
./max-mock-linux-amd64 -config config.yaml
```

Любое поле можно переопределить окружением — удобно в контейнерах и unit-файлах:

| Переменная | Что задаёт |
|---|---|
| `MAXMOCK_LISTEN` | адрес прослушивания |
| `MAXMOCK_PUBLIC_BASE_URL` | публичный адрес мока |
| `MAXMOCK_DB_PATH` | путь к файлу базы |
| `MAXMOCK_BLOB_DIR` | каталог загруженных файлов |
| `MAXMOCK_TLS_CERT_FILE` | сертификат сервера (включает HTTPS вместе со следующей) |
| `MAXMOCK_TLS_KEY_FILE` | приватный ключ сервера |
| `MAXMOCK_WEBHOOK_CA_FILE` | CA контура для проверки сертификатов стендов |
| `MAXMOCK_WEBHOOK_INSECURE_SKIP_VERIFY` | `1`/`true`/`yes` — не проверять сертификаты стендов |
| `MAXMOCK_LOG_FORMAT` | `text` или `json` |
| `MAXMOCK_LOG_LEVEL` | `debug`, `info`, `warn`, `error` |
| `MAXMOCK_LOG_BODY_LIMIT` | байт тела в строке лога; `0` — не печатать тела |

### Что видно в консоли

Мок пишет в stderr строку на каждый вызов Bot API, каждое действие
тестировщика в веб-чате и каждую попытку доставки вебхука — с телами запроса и
ответа. По этому логу разбирается интеграция, не открывая UI:

```
level=INFO  msg="Bot API" method=POST path=/messages status=200 ms=1 bot=1 chat=3003011655588571 req="{...}" resp="{...}"
level=ERROR msg="вебхук →" type=message_created url=http://stand:8080/hook status=0 попытка=1/3 error="dial tcp: connection refused"
level=WARN  msg="событие никуда не ушло" type=bot_started bot=1 причина="нет подписки на этот тип события"
```

`4xx` печатается как `WARN`, `5xx` и несостоявшаяся доставка — как `ERROR`,
поэтому отказ видно и при `level: warn`. Уровень на один запуск задаётся
флагом: `./max-mock -log-level debug` — добавится фон (статика, страницы,
`/healthz`).

Токен бота и секрет подписки в лог не попадают: они приходят заголовками, а
заголовки не печатаются. Тела заливаемых и отдаваемых файлов заменяются
размером. Обрезка тела по `body_limit` касается только лога — обработчик
получает запрос целиком.

### Запуск по HTTPS

Мок слушает TLS на **том же порту**, как только в конфиге заданы оба файла
пары. Второго порта и редиректа с HTTP нет: поведение POST после редиректа
различается между клиентами, и для API это ловушка, а не удобство.

```yaml
listen: ":8443"
public_base_url: "https://max-mock.stand.local:8443"

tls:
  cert_file: "/etc/max-mock/tls/server.crt"
  key_file:  "/etc/max-mock/tls/server.key"
```

> **`public_base_url` обязан стать `https://`.** При включённом TLS мок с
> `http://` в этом поле не стартует и скажет почему: иначе стенды получили бы
> upload-адреса и ссылки на вложения по схеме, которой на порту уже нет, и
> отказ всплыл бы позже и в чужом месте — как «стенд не может скачать файл».

Если сертификата от администратора контура нет, самоподписанный выпускается
одной командой. **Имена в SAN обязательны** — по одному CN современные
клиенты не проверяют:

```bash
openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
  -keyout server.key -out server.crt \
  -subj "/CN=max-mock.stand.local" \
  -addext "subjectAltName=DNS:max-mock.stand.local,IP:10.0.0.7"
```

Перечислите здесь **все** адреса, по которым к моку обращаются стенды: имя
из `public_base_url`, все алиасы, IP при обращении по адресу.

При старте мок печатает, с каким сертификатом поднялся, — этой строки хватает,
чтобы разобрать большинство отказов подключения, не запуская `openssl` на
боевом хосте:

```
max-mock: контракт 0.0.33, слушаю https://:8443
max-mock: сертификат max-mock.stand.local (SAN: max-mock.stand.local, 10.0.0.7), действителен до 2028-11-08
```

Проверка: `curl --cacert server.crt https://max-mock.stand.local:8443/healthz`
должен ответить `ok`.

**Стендам нужно доверять этому сертификату.** Для самоподписанного —
добавить `server.crt` в доверенные: в системное хранилище
(`/usr/local/share/ca-certificates/` + `update-ca-certificates` на Debian,
`/etc/pki/ca-trust/source/anchors/` + `update-ca-trust` на RHEL) либо в
truststore приложения (для Java — `keytool -importcert` в `cacerts`).

### Доставка на стенды по HTTPS

Обратная сторона: стенды КЦ сами живут на `https://` с сертификатами
внутреннего центра. Мок ходит на них штатным клиентом и без настройки
получит `x509: certificate signed by unknown authority`.

```yaml
webhook:
  ca_file: "/etc/max-mock/tls/stand-ca.crt"   # CA контура
  insecure_skip_verify: false
```

`ca_file` **добавляется** к системным корневым, а не заменяет их: стенды на
публичных сертификатах продолжают работать. Если CA взять неоткуда, а
демонстрация сегодня — `insecure_skip_verify: true` отключает проверку
целиком; мок предупреждает об этом при каждом старте, чтобы временная мера
не стала постоянной незаметно.

### Как служба systemd

```ini
# /etc/systemd/system/max-mock.service
[Unit]
Description=max-mock — эмулятор бот-платформы Max
After=network.target

[Service]
Type=simple
User=max-mock
WorkingDirectory=/opt/max-mock
ExecStart=/opt/max-mock/max-mock -config /opt/max-mock/config.yaml
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo useradd --system --home /opt/max-mock max-mock
sudo mkdir -p /var/lib/max-mock && sudo chown max-mock: /var/lib/max-mock
sudo systemctl enable --now max-mock
sudo journalctl -u max-mock -f
```

### Обновление версии

Состояние живёт в файле базы, а не в бинарнике: замените файл и перезапустите
службу. Схема базы при необходимости мигрируется автоматически при старте —
ранее созданные боты, диалоги и подписки сохраняются.

```bash
sudo systemctl stop max-mock
sudo cp max-mock-linux-amd64 /opt/max-mock/max-mock
sudo systemctl start max-mock
```

## 4. Один мок на несколько стендов

Так и задумано. Каждый стенд регистрирует **свой URL** через
`POST /subscriptions` **своим токеном бота**:

- один бот, несколько подписок — событие уйдёт на все URL сразу;
- разные боты (st / ift / dev) — полностью независимые состояния, диалоги и
  журналы; тестировщики работают параллельно, каждый по своей закладке
  `/mock/chat/{botId}`.

Фильтр `update_types` в подписке работает: стенд получит только те события,
которые заказал.

## 5. Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| `401` с кодом `verify.token` | токена нет, он неверен или передан не так. В заголовке должен быть ровно токен: `Authorization: <token>` — без `Bearer` и без `?access_token=` в URL. Текст в поле `message` различает случаи: `No access token`, `Malformed access token` (передана схема `Bearer`), `Invalid access_token` (токен неизвестен). Токен виден в админке |
| `404` с кодом `mock.not_implemented` | путь вне объёма мока: `/chats*`, `GET /updates` (long polling), `GET /videos/{videoToken}`. Остальные пути реализованы |
| `400` с кодом `mock.validation` | запрос не прошёл проверку по OpenAPI. В поле `message` — конкретное поле и причина; то же видно во вкладке «Журнал» |
| `400` с `mock.chat.not_found` | `user_id`/`chat_id` неизвестен. Клиента нужно сначала создать в веб-чате |
| Кнопка в чате серая, нажать нельзя | это `chat` или `open_app` — вне объёма мока. Остальные шесть типов работают |
| Нажал кнопку «поделиться контактом», пришёл отказ | у клиента не заполнен телефон. Он не в схеме пользователя Max, поэтому задаётся только в карточке клиента |
| Бот попросил геопозицию, но ничего не ушло | у клиента нет координат, а кнопка была с `quick: true` — то есть без запроса. Заполните координаты в карточке |
| `409` с кодом `mock.conflict` | клиент с таким `user_id` уже заведён. Возьмите другой либо работайте с существующим |
| В событии нет `last_name` | фамилия не заполнена в карточке клиента; контракт объявляет поле nullable, и мок не выдумывает значение |
| События не приходят на стенд | вкладка «Доставки»: там видны статус ответа стенда, номер попытки и текст ошибки. Мок повторяет доставку при 5xx и сетевых сбоях, при 4xx — нет |
| Конкретное событие не пришло на стенд, хотя остальные приходят | вкладка «События»: если карточка помечена «событие не отправлено», вместо кода стоит «нет ответа», а ниже красным «нет подписки на этот тип события», доставки не было вовсе — стенд не подписан на этот тип в `update_types`, а не мок его не отправил |
| Стенд ответил 200, но ничего не сделал | вкладка «События», в карточке «max → бот» блок «стенд ответил»: там лежит тело его ответа. Пустой 200 — стенд событие принял и промолчал; тело с ошибкой покажет, на чём он споткнулся |
| Стенд не может скачать вложение | `public_base_url` указывает на `localhost`. Пропишите адрес, по которому мок виден со стенда |
| В «Доставках» — `x509: certificate signed by unknown authority` | мок не доверяет сертификату стенда. Пропишите CA контура в `webhook.ca_file`; если его взять неоткуда — временно `webhook.insecure_skip_verify: true` |
| Стенд не подключается к моку: `certificate is not valid for …` | в SAN сертификата мока нет имени, по которому стенд обращается. Сверьте строку «сертификат …» в логе старта с `public_base_url` и перевыпустите с нужным `subjectAltName` |
| Клиент КЦ получает `Client sent an HTTP request to an HTTPS server` | адрес мока на стенде остался с `http://`. Порт слушает только TLS, редиректа нет намеренно |
| Мок не стартует: `TLS включён, а public_base_url … начинается с http://` | смените схему в `public_base_url` на `https://` |
| Мок не стартует: `задан tls.cert_file, но не задан tls.key_file` | перенесена половина пары; нужны оба файла |
| После перезапуска пропали боты | открыт другой файл базы: путь по умолчанию относительный. Сверьте строку «состояние — база …» в логе; задайте абсолютный `db_path`. Второй возможный источник — `make reset` или удаление `max-mock.db` вручную |
| `500` с кодом `mock.internal` | ответ самого мока разошёлся с контрактом. Это дефект мока — сообщите, тело ошибки содержит подробности |
| Порт занят | `MAXMOCK_LISTEN=":9090" ./max-mock` |

Полезные адреса:

```
GET /healthz                              проверка живости
GET /mock                                 админка ботов
GET /mock/chat/{botId}                    веб-чат тестировщика
GET /mock/api/log?limit=50                общий журнал вызовов Bot API
GET /mock/api/bots/{id}/deliveries        журнал доставок webhook-ов
```

## 6. Проверка самого мока

```bash
make test    # все тесты, включая сквозные
make e2e     # только сквозной сценарий интеграции, подробным выводом
```

Сквозной тест поднимает мок и фейковый стенд, проходит полный путь и
проверяет **обе стороны обмена по контракту**: каждый ответ мока — против
`openapi.MaxBotApi.yaml`, каждое событие — против `openapi.MaxBotWebhook.yaml`.

После обновления OpenAPI-артефактов из maxapi:

```bash
make sync-specs
```

Цель копирует свежие yaml и сразу прогоняет валидацию и сквозные тесты —
расхождения видно немедленно, а не на стенде КЦ.
