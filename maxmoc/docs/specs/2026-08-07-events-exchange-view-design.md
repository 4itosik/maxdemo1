# Дизайн: лента событий как обмены «запрос → ответ»

**Дата:** 2026-08-07 · **Затрагивает:** `internal/store`, `internal/webhook`,
`web/static`, документацию, тесты

## Задача

Вкладка «События» показывает три вида строк вперемешку — действие тестировщика
в веб-чате, доставку на стенд, вызов Bot API от бота, — и по ней всё равно не
читается главное: **кто с кем чем обменялся**.

Действия UI лишние: тестировщик только что сам нажал кнопку, и напоминание об
этом занимает строку. Ошибку действия он и так видит алертом сразу
(`chat.js`, `act()`).

Остальные две строки — половинки одного разговора, но выглядят как
разнородный лог. Тестировщику нужна пара:

- **max → бот**: мок прислал на стенд вот такой JSON — стенд ответил вот так;
- **бот → max**: бот прислал в мок вот такой JSON — мок ответил вот так.

Второе направление уже хранится целиком: у `request_log` есть и
`request_body`, и `response_body`. Первое хранится наполовину — тело ответа
стенда `Dispatcher.post` сливает в `io.Discard`, в журнале остаётся один
HTTP-статус. Симметрию надо восстановить в хранилище, иначе на фронте её
неоткуда взять.

## Дизайн

### 1. Ответ стенда начинает сохраняться

`webhook_deliveries` получает столбец:

```sql
response_body TEXT NOT NULL DEFAULT ''
```

В `schema.sql` — в объявлении таблицы, для существующих баз — строкой
`ALTER TABLE webhook_deliveries ADD COLUMN response_body TEXT NOT NULL DEFAULT ''`
в списке `migrations`, как уже сделано для `chat_id`.

`Dispatcher.post` вместо `io.Copy(io.Discard, resp.Body)` читает тело через
`io.LimitReader` с потолком **8 КиБ**. При превышении в конец дописывается
`…(обрезано, всего N байт)`.

Потолок обязателен, а не «на всякий случай»: стенд, упавший в 500, отвечает
HTML-страницей ошибки, и без ограничения она осядет в БД на каждой из трёх
попыток каждого события.

Обрыв соединения на чтении тела **не отменяет уже полученный статус**:
`status` остаётся, причина дописывается в `error`, `response_body` — то, что
успело прочитаться. Иначе «стенд ответил 200, но связь оборвалась» стало бы
неотличимо от «стенд не ответил вовсе».

Сигнатура `post` возвращает теперь ещё и тело:

```go
func (d *Dispatcher) post(sub store.Subscription, body []byte) (postResult, error)

type postResult struct {
    Status   int
    Body     string
    Duration time.Duration
}
```

Структура, а не четвёртое возвращаемое значение: три анонимных числа подряд на
месте вызова читаются хуже, чем поля.

`store.DeliveryEntry` получает поле `ResponseBody string` с тегом
`json:"response_body,omitempty"`, `LogDelivery` и оба сканера — новый столбец.

### 2. Лента: только обмены этого диалога

`internal/store/feed.go`:

- ветка `ui` уходит из `ListDialogEvents`, поле `UI` — из `DialogEvent`,
  `feedRank` остаётся с двумя видами;
- `listDialogRequests` теряет `OR chat_id IS NULL`. Вызовы бота вне диалога
  (`GET /me`, `PATCH /me/commands`, подписки, загрузки) больше не подмешиваются
  в каждый диалог — они остаются на вкладке «Журнал», где показаны в разрезе
  бота, которому и принадлежат.

Порядок ленты не меняется: **новые сверху**, как в «Журнале» и «Доставках».
В одну миллисекунду вызов бота стоит выше доставки — доставка причина, а лента
идёт от новых к старым.

`ui_actions`, `LogUIAction` и `ListUIActions` **остаются**: действия
тестировщика продолжают журналироваться и их можно достать запросом при
разборе. Читателя в UI у них теперь нет — это записывается комментарием у
`LogUIAction`, чтобы отсутствие вызова из фронта не выглядело обрывом.

Событие шины `KindUIAction` тоже остаётся — его публикует `logAction`, и
фронт просто перестаёт на него реагировать.

### 3. Интерфейс: карточка обмена

`renderEvents` рисует один тип карточки вместо трёх типов строк. Шапка,
цветная полоса слева по направлению и два подписанных блока.

Полоса берёт цвета из существующих переменных темы: `max → бот` —
акцентный цвет мока, `бот → max` — нейтральный серый. Направление дублируется
словами в шапке: цвет один не должен нести смысл.

```
┃ max → бот        message_created   200   12:04:11
┃
┃  ▸ отправлено   POST https://stand/hook
┃  ┌─────────────────────────────────────────────┐
┃  │ { "update_type": "message_created",         │
┃  │   "message": { "body": {"text": "привет"} } }│
┃  └─────────────────────────────────────────────┘
┃  ◂ стенд ответил   200 OK · 43 мс
┃  ┌─────────────────────────────────────────────┐
┃  │ (пустое тело)                               │
┃  └─────────────────────────────────────────────┘

┃ бот → max        POST /messages    200   12:04:12
┃
┃  ▸ бот прислал
┃  ┌─────────────────────────────────────────────┐
┃  │ { "chat_id": 42, "text": "Здравствуйте!" }  │
┃  └─────────────────────────────────────────────┘
┃  ◂ max ответил     200 · 3 мс
┃  ┌─────────────────────────────────────────────┐
┃  │ { "message": { "mid": "mid.a3f…", … } }     │
┃  └─────────────────────────────────────────────┘
```

Откуда что берётся:

| | `delivery` | `request` |
|---|---|---|
| направление | `max → бот` | `бот → max` |
| заголовок | `update_type` | `METHOD /path?query` |
| подзаголовок запроса | `POST {url}` | — |
| тело запроса | `body` | `request_body` |
| подпись ответа | `стенд ответил` | `max ответил` |
| тело ответа | `response_body` | `response_body` |
| статус, длительность | `status`, `duration_ms` | `status`, `latency_ms` |

Частные случаи:

- **`url` пуст** — событие никуда не ушло: нет подписки на этот тип либо тело
  не прошло валидацию по webhook-контракту. Блок ответа заменяется красной
  строкой с причиной из `error`, подзаголовок запроса — словом «не отправлено».
- **Повторы** — каждая попытка отдельной карточкой, в шапке `попытка 2`.
  Не группируются: у попытки свой ответ, свой статус и своё время, склейка их
  спрячет. Общее число попыток карточке неизвестно — в журнале лежит только
  номер, а конфигурация повторов на фронт не отдаётся.
- **Сетевая ошибка** (`status == 0`, заполнен `error`) — вместо бейджа статуса
  «нет ответа», вместо блока ответа красная строка с текстом ошибки.
- **Пустое тело** — приглушённое `(пустое тело)`, а не пустой блок. Это
  осмысленный ответ: стенд принял событие и ничего не вернул.
- **Тело запроса пусто** (`GET`, `DELETE`) — вместо блока JSON приглушённая
  строка `(без тела)`; сам запрос уже описан заголовком карточки.
- **Тело не JSON** — `pretty()` уже отдаёт такое как есть; HTML-страница
  ошибки от упавшего стенда покажется текстом.
- **JSON длиннее 18 строк** — блок ограничен по высоте и разворачивается
  кнопкой «развернуть». Один `message_created` в развёрнутом виде занимает
  экран целиком, и лента перестаёт быть лентой.

Живое обновление (`chat.js`, `ws.onmessage`):

- из списка kind'ов, обновляющих ленту, уходит `ui_action`;
- уходит условие `event.chat_id === undefined`: вызовы вне диалога в ленте
  больше не показываются, перерисовывать по ним нечего. Остаётся строгое
  `event.chat_id === state.chatID`.

Вкладки «Журнал» и «Доставки» не трогаются: они показывают всё по боту и
остаются местом, где видно вызовы вне диалога.

## Тесты

| Уровень | Что проверяется |
|---|---|
| `store` | миграция старой базы добавляет `response_body`, данные на месте; `LogDelivery` сохраняет и читает тело ответа |
| `store` (feed) | лента не отдаёт `ui`; лента не отдаёт вызовы с `chat_id IS NULL`; порядок «новые сверху» и вызов бота выше доставки в одну миллисекунду |
| `webhook` | стенд отвечает телом → оно доехало в `ResponseBody`; тело больше 8 КиБ → обрезано с маркером; обрыв на чтении тела → статус сохранён, причина в `error` |
| `httpserver` | `GET /mock/api/dialogs/{chatId}/events` возвращает только `delivery` и `request` этого диалога |
