# Дизайн: старт/стоп диалога, лента событий и меню команд

**Дата:** 2026-08-06 · **Затрагивает:** `internal/store`, `internal/core`,
`internal/controlapi`, `internal/maxfacade`, `internal/webhook`,
`internal/wire`, `web/static`, документацию, тесты

## Задача

Три дыры, из-за которых по моку не читается ход разговора. Все три вылезли из
одного разбора: тестировщик набрал в веб-чате `/start` текстом, стенд ответил
приветствием с клавиатурой, клиент нажал кнопку — и восстановить по журналам,
что именно произошло и почему, оказалось нельзя.

**1. Событие старта нельзя послать повторно.** Кнопка «Начать» шлёт настоящий
`bot_started`, но прячется после первого нажатия, а `ClientStart` гасит
повторный вызов. Проверить обработку старта второй раз — только заведя нового
клиента. При этом контракт прямо говорит, что событие приходит, когда
пользователь «начнёт **или возобновит** общение с ботом», то есть повторный
старт в живом Max есть — после остановки.

**2. Журналы разорваны надвое, а действий тестировщика в них нет вовсе.**
`request_log` знает, что бот прислал в мок; `webhook_deliveries` — что мок
отправил боту. Лежат на разных вкладках, оба в разрезе бота, без привязки к
диалогу. Действия из веб-чата не журналируются нигде: control-API не пишет в
журнал. Причина и следствие оказываются в разных местах, и связать их можно
только по времени и глазами.

**3. Команды бота в веб-чате не видны.** `PATCH /me/commands` мок принимает и
хранит, `GET /me` их отдаёт — но тестировщику показать негде. В живом Max
человек видит меню команд и выбирает `/start` оттуда; на моке приходится
набирать руками, и различие между «нажал Начать» и «набрал /start» стирается.
Ровно на этом и запутался разбор.

## Два разных пути к боту

Спека нужна прежде всего затем, чтобы эти пути больше не смешивались.

| Действие человека в Max | Что уходит боту |
|---|---|
| нажал «Начать» в настройках бота | `bot_started` с `chat_id`, `user`, `payload` диплинка; **сообщения нет** |
| выбрал команду в меню или набрал её | обычное `message_created` с текстом `/start` |
| остановил бота в настройках | `bot_stopped` с `chat_id` и `user` |

В веб-чате им соответствуют кнопка «Начать»/«Остановить» и полоса чипов с
командами — два разных элемента интерфейса, а не один.

## Дизайн

### 1. Старт и остановка диалога

`bot_stopped` мок сейчас не умеет вовсе — он появляется как полноценное
исходящее событие. По контракту обязательны `update_type`, `chat_id`, `user`;
`user_locale` доступен в диалогах.

```go
// wire
const UpdateBotStopped = "bot_stopped"

type BotStoppedUpdate struct {
    UpdateBase
    ChatID     int64   `json:"chat_id"`
    User       User    `json:"user"`
    UserLocale *string `json:"user_locale,omitempty"`
}

// core — зеркало ClientStart
func (c *Core) ClientStop(chatID int64) error

// store — зеркало SetDialogStarted, возвращает changed
func (s *Store) SetDialogStopped(chatID int64) (bool, error)
```

Оба действия идемпотентны: старт начатого диалога и остановка остановленного
не делают ничего и события не шлют. После остановки старт снова срабатывает —
это и есть «возобновит общение» из контракта.

Control-API получает действие `stop` рядом с существующим `start`.

В веб-чате одна кнопка меняет роль по состоянию диалога: «Начать», пока
диалог не начат, «Остановить» — пока начат. Бейдж «не начат» в списке
клиентов уже показывает это состояние и остаётся.

**Решение: остановленный диалог не запрещает боту слать в него сообщения.**
Как ведёт себя живой Max — не измерено. Запрет выглядел бы правдоподобно, но
мок не выдумывает поведение: это тот же принцип, по которому в README уже
записаны неизмеренные расхождения. Ограничение появится, когда будет замер.

### 2. Лента событий диалога

#### Хранилище

`chat_id` добавляется в оба существующих журнала — миграцией `ALTER TABLE` в
списке `migrations`, как заведено. `NULL` означает «операция не про диалог».

Действия тестировщика получают свою таблицу: у них нет ни метода с путём, ни
url с попыткой, и класть их в чужую схему значит держать половину столбцов
пустыми.

```sql
CREATE TABLE IF NOT EXISTS ui_actions (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    ts      INTEGER NOT NULL,
    bot_id  INTEGER NOT NULL,
    chat_id INTEGER NOT NULL,
    action  TEXT    NOT NULL,            -- start, stop, send, press, edit, …
    detail  TEXT    NOT NULL DEFAULT '', -- параметры действия, JSON
    error   TEXT    NOT NULL DEFAULT ''  -- пусто, если действие удалось
);
CREATE INDEX IF NOT EXISTS idx_ui_actions_chat_ts ON ui_actions(chat_id, ts DESC);
```

`detail` — тело запроса control-API как есть: текст сообщения, `mid`,
`payload` нажатой кнопки. Без нормализации: лента должна показывать, что
тестировщик на самом деле отправил, а не то, во что мок это превратил.

К обоим мигрируемым журналам добавляются индексы по `(chat_id, ts DESC)` —
лента читает именно так, а существующие индексы по `(bot_id, ts)` для этого
не годятся.

Три таблицы вместо одной — сознательный выбор. Общая таблица `events`
потребовала бы свести к общему знаменателю три разных набора полей: у вызова
Bot API это метод, путь, статус и латентность, у доставки — url, тип события и
номер попытки, у действия UI — свои параметры. Плоская схема либо теряет
типизацию, либо превращает `detail` в свалку. Слияние двух-трёх сотен записей
по времени на чтении стоит дешевле, чем эта потеря: мок не нагрузочный стенд.

#### Кто пишет действия UI

Control-API, а не ядро. Ядро одинаково обслуживает и бота, и веб-чат, и знать,
что вызывающий — интерфейс тестировщика, ему незачем. Control-API же и есть
поверхность UI: он видит и название действия, и его параметры.

Пишутся действия в диалоге — `start`, `stop`, `send`, `send_contact`,
`send_location`, `press`, `edit`, `delete` — и создание клиента, которому
достаётся `chat_id` заведённого диалога. Неудачное действие пишется тоже, с
текстом ошибки: «нажал, ничего не произошло» — самая частая жалоба, и она
должна быть видна в ленте.

#### Откуда `chat_id` у вызова Bot API

Не из разбора query: у половины операций диалог определяется телом или
идентификатором сущности. Его сообщает сам обработчик — он и так резолвит
диалог, сообщение или нажатие:

| Операция | Источник `chat_id` |
|---|---|
| `POST /messages`, `GET /messages` | `chat_id`/`user_id` запроса |
| `PUT`, `DELETE /messages`, `GET /messages/{messageId}` | сообщение по `mid` |
| `POST /answers` | нажатие по `callback_id` |
| `GET /me`, `PATCH /me/commands`, `/subscriptions`, `/uploads` | нет диалога, `NULL` |

Middleware кладёт в контекст запроса ячейку, обработчик заполняет её вызовом
`noteChat(r, chatID)`, `finish` читает при записи журнала. Обработчик, который
ячейку не тронул, даёт `NULL` — и это правильный ответ для операций из
последней строки таблицы.

#### Недоставленные события

Сейчас событие, на тип которого никто не подписан, `Dispatcher.process`
молча пропускает. Именно поэтому разбор упирался в тупик: `message_edited` от
ответа на нажатие генерировался, но в журналах его не было — и выглядело это
как «мок не отправил».

Дальше диспетчер пишет в `webhook_deliveries` запись с пустым `url`, `status`
0 и пояснением «нет подписки на этот тип события». Отказ по валидации
контракта так уже логируется (`logRejected`), новая запись встаёт рядом.

#### Чтение

```
GET /mock/api/dialogs/{chatId}/events?limit=200
```

Отдаёт слитый по времени список записей с полем-тегом: `ui`, `delivery`,
`request`. Берутся записи диалога плюс вызовы Bot API без диалога у того же
бота — `PATCH /me/commands` и переподписка относятся ко всему боту, но
показывать их надо там, где на них смотрят. В ленте они помечены «без
диалога».

#### Интерфейс

Вкладка «События» встаёт второй: Чат · События · Журнал · Доставки.
Существующие вкладки остаются — они показывают всё по боту, и это отдельная
полезная оптика.

```
14:36:25  UI      Иван нажал «Начать»
14:36:25  → стенд bot_started        200   12 мс
14:36:25  ← бот   POST /messages     200    8 мс   {"text":"Здравствуйте…"}
14:36:37  UI      Иван нажал кнопку «Привет» (payload hello)
14:36:37  → стенд message_callback   200    9 мс
14:36:37  ← бот   POST /answers      200    6 мс   {"message":{"text":"Вы нажали: Привет"}}
14:36:37  → стенд message_edited      —          нет подписки
```

Тела запроса и ответа раскрываются по клику: они уже хранятся, просто лежат
сейчас на разных вкладках. Живое обновление — через существующую шину, к
которой добавляется вид события `ui_action`.

Связывание строк в цепочку — намеренно не делается. Честного идентификатора
трассы нет: вызов бота обратно в мок ничего о породившем его событии не несёт,
и «цепочка» была бы догадкой по времени и `chat_id`. Хронология по одному
диалогу даёт то же понимание, ничего не выдумывая.

### 3. Меню команд

Полоса чипов над полем ввода, наполняется из `bot.commands` — control-API уже
отдаёт это поле в `GET /mock/api/bots/{id}`, на бэкенде делать нечего.

- клик по чипу отправляет обычное текстовое сообщение `/name`, то есть
  `message_created`, — ровно как выбор команды в живом клиенте Max;
- `description` из `PATCH /me/commands` уходит во всплывающую подсказку: голое
  `/buttons` тестировщику ни о чём не говорит;
- пустой список команд прячет полосу целиком. По контракту `[]` в `PATCH
  /me/commands` — это «удалить все команды», а отсутствие поля ничего не
  меняет; полоса следует за состоянием;
- полосы нет и когда бот вовсе не звал `PATCH /me/commands`. Это само по себе
  диагностика: команд у бота нет.

Чтобы полоса обновлялась без перезагрузки, `EditMyCommands` начинает
публиковать событие в шину — сейчас он молчит. Веб-чат по нему перечитывает
бота.

## Тесты

| Уровень | Что проверяется |
|---|---|
| `store` | миграция старой базы: `chat_id` добавляется, данные и боты на месте; `SetDialogStopped` возвращает `changed` один раз; чтение `ui_actions` |
| `core` | `ClientStop` шлёт `bot_stopped`; повторная остановка молчит; старт после остановки шлёт `bot_started` второй раз; оба события валидны по `openapi.MaxBotWebhook.yaml`, как и все существующие |
| `webhook` | событие без подписки даёт запись в журнале с пояснением, а не тишину |
| `controlapi` | действие `stop`; каждое действие диалога оставляет запись в `ui_actions`, неудачное — с текстом ошибки; лента отдаёт три вида записей в порядке убывания времени и подмешивает вызовы без диалога того же бота |
| `maxfacade` | `chat_id` проставляется для операций из таблицы выше и остаётся `NULL` для `GET /me`, `PATCH /me/commands`, подписок и загрузок |
| сквозной | «начать → выбрать команду из меню → нажать кнопку → остановить»: в ленте диалога присутствуют все звенья, включая недоставленное `message_edited` |
