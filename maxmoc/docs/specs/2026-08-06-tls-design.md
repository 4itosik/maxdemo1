# Дизайн: TLS в max-mock

**Дата:** 2026-08-06 · **Затрагивает:** `internal/tlsconf` (новый),
`internal/config`, `internal/webhook`, `cmd/max-mock`, документацию, тесты

## Задача

Мок сегодня умеет только `http://`. Этого не хватает по трём причинам.

1. **Контракт Max требует `https://`.** Клиентские библиотеки КЦ, написанные
   по документации, часто отказываются ходить на `http://` вовсе. Обещание
   README — «переезд с прода на мок это замена базового адреса, и больше
   ничего» — на таких стендах не выполняется.
2. **Политика контура.** В закрытых контурах межсервисный трафик по
   открытому HTTP нередко просто запрещён правилами.
3. **Обратная сторона.** Стенды КЦ сами живут на `https://` с сертификатами
   внутреннего CA. Диспетчер вебхуков ходит на них клиентом по умолчанию и
   падает с `x509: certificate signed by unknown authority` — доверять
   контурному CA нечем.

## Объём

Входит:

- входящий HTTPS на том же порту, сертификат и ключ — файлами из конфига;
- доверие при исходящей доставке вебхуков: CA-файл контура, аварийное
  отключение проверки.

Не входит намеренно:

- **автогенерация самоподписанного сертификата.** Сертификат, который мок
  выпустил сам, всё равно надо разнести по доверенным на каждом стенде — то
  есть ручная работа никуда не девается, а в логе появляется ещё один
  источник путаницы («какой из трёх сертификатов сейчас действует»). Выпуск
  остаётся у администратора контура, документация даёт готовую команду;
- **mTLS.** В контуре доступ к сервисам так не устроен;
- **второй порт и редирект с HTTP.** Редирект для API — ловушка: поведение
  POST после `301` различается между клиентами, и отладка такого отказа
  дороже, чем разовая замена адреса на стендах;
- **настройка набора шифров.** Значения Go по умолчанию для TLS 1.2+
  соответствуют требованиям, а ручка добавляет способ сделать хуже.

## Конфигурация

```yaml
listen: ":8443"
public_base_url: "https://max-mock.stand.local:8443"

tls:
  cert_file: "/etc/max-mock/tls/server.crt"   # PEM, вместе с промежуточными
  key_file:  "/etc/max-mock/tls/server.key"

webhook:
  timeout_sec: 10
  retries: 2
  backoff_sec: [1, 5]
  ca_file: "/etc/max-mock/tls/stand-ca.crt"   # пусто — системные корневые
  insecure_skip_verify: false
```

TLS включается наличием обоих файлов. Пустой блок `tls` — обычный HTTP,
как сегодня; существующие конфиги продолжают работать без правок.

Переменные окружения поверх файла, как у остальных полей:

| Переменная | Что задаёт |
|---|---|
| `MAXMOCK_TLS_CERT_FILE` | сертификат сервера |
| `MAXMOCK_TLS_KEY_FILE` | приватный ключ |
| `MAXMOCK_WEBHOOK_CA_FILE` | CA для проверки стендов |
| `MAXMOCK_WEBHOOK_INSECURE_SKIP_VERIFY` | `1`/`true`/`yes` — не проверять сертификаты стендов |

### Проверки на старте

Каждая — отказ запуска с внятным сообщением, а не молчаливое расхождение:

1. **Задан только `cert_file` или только `key_file`.** Сообщение называет
   недостающий.
2. **TLS включён, а `public_base_url` начинается с `http://`.** Иначе
   upload-адреса и ссылки на вложения ведут на схему, которой на порту уже
   нет. Отказ всплыл бы у КЦ поздно и в чужом месте — как «стенд не может
   скачать вложение». Обратное сочетание (`https://` без TLS) ошибкой не
   считается: так выглядит мок за терминирующим прокси.
3. **Сертификат и ключ читаются и совпадают между собой.** Загрузка идёт
   до начала обслуживания, поэтому битый путь, отобранные права или чужой
   ключ видны сразу, а не при первом подключении стенда.

`insecure_skip_verify: true` запуску не мешает, но печатает предупреждение
при каждом старте: временная мера не должна становиться постоянной незаметно.

## Пакет `internal/tlsconf`

Два конструктора и ничего больше; про мок и его конфиг пакет не знает —
на входе пути, на выходе `*tls.Config`.

```go
// ServerConfig грузит пару и собирает конфигурацию слушателя.
func ServerConfig(certFile, keyFile string) (*tls.Config, CertInfo, error)

// ClientConfig собирает конфигурацию клиента доставки.
func ClientConfig(caFile string, insecure bool) (*tls.Config, error)
```

`MinVersion` выставляется в TLS 1.2 явно: у сервера Go нижняя граница по
умолчанию ниже, и полагаться на неё не стоит.

`CertInfo` — CN, список SAN и дата истечения. Уходит в стартовый лог: в
закрытом контуре это первый ответ на «почему браузер ругается» и «почему
стенд не подключается», и он должен быть виден без `openssl x509` на боевом
хосте.

Заданный `caFile` **добавляется** к системному пулу, а не заменяет его.
В контуре часть стендов обычно на внутреннем CA, часть на публичном
сертификате; замена пула тихо ломает вторые. Если системный пул недоступен
(экзотический образ без набора корневых), берётся пустой пул с одним лишь
CA из файла — это по-прежнему рабочая конфигурация, а не отказ.

## Точки подключения

**`cmd/max-mock/main.go`** — развилка на одном порту:

```go
if cfg.TLS.Enabled() {
    srv.TLSConfig = tlsCfg
    err = srv.ListenAndServeTLS("", "")   // пара уже в TLSConfig
} else {
    err = srv.ListenAndServe()
}
```

Стартовый лог печатает схему и описание сертификата:

```
max-mock: контракт 0.0.32, слушаю https://:8443
max-mock: сертификат max-mock.stand.local (SAN: max-mock.stand.local, 10.0.0.7), действителен до 2027-08-06
```

**`internal/webhook`** — `New` возвращает `(*Dispatcher, error)`: пакет сам
собирает транспорт, клонируя `http.DefaultTransport` и подставляя
`TLSClientConfig`. Владение остаётся там же, где таймауты и повторы доставки,
а ошибка чтения CA-файла всё равно возникает на старте, потому что `New`
вызывается на старте. Клонирование, а не свой `&http.Transport{}` — чтобы не
потерять пулинг соединений и поддержку прокси из окружения.

**`internal/httpserver`** не меняется: TLS живёт уровнем ниже обработчиков.

## Тесты

Сертификаты генерируются в самих тестах (`crypto/x509` + ECDSA, срок — час);
в репозиторий не кладётся ни одного ключа.

| Пакет | Что проверяется |
|---|---|
| `tlsconf` | загрузка пары; внятная ошибка на битом ключе и на ключе от другого сертификата; `CertInfo` содержит SAN и срок; клиент с `ca_file` доверяет серверу этого CA; клиент без `ca_file` ему не доверяет; `insecure` отключает проверку |
| `config` | `cert` без `key` и наоборот — ошибка; `http://` в `public_base_url` при включённом TLS — ошибка; `https://` без TLS — не ошибка; env-переопределения, включая разбор булевой переменной |
| `webhook` | доставка на `httptest.NewTLSServer`: проходит с его CA в `ca_file`, падает с x509-ошибкой без него, проходит с `insecure_skip_verify`. Главный тест объёма — проверяет живую цепочку, а не конструктор |
| сквозной | мок поднят под TLS: `GET /healthz` через клиент с его CA отвечает `ok` |
