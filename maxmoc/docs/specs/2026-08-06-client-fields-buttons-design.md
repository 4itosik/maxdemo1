# Дизайн: карточка клиента и работающие кнопки

**Дата:** 2026-08-06 · **Затрагивает:** `internal/store`, `internal/core`,
`internal/controlapi`, `internal/wire`, `web/static`, документацию, тесты

## Задача

Две дыры, из-за которых КЦ не может проверить на моке половину своих
сценариев.

**1. Клиент почти безымянный.** В карточке есть только `first_name` и
`username`. КЦ, получив `message_created`, видит пользователя без фамилии и
без всякой возможности связать его со своей записью абонента. Телефон —
основной ключ связывания в контакт-центре — мок отдать не может вовсе.

**2. Кнопки не нажимаются.** Веб-чат оживляет два типа из восьми:
`callback` и `link`. Нажатие на `request_contact` или `request_geo_location`
показывает подсказку «моком не обрабатывается», то есть сценарий «бот просит
телефон — абонент делится — КЦ связывает с карточкой» на моке непроверяем.
Ровно этот сценарий у КЦ первый в очереди.

## Что куда доезжает

Решает, какие поля вообще имеет смысл заводить: поле, которому в контракте
некуда ехать, — мёртвый груз.

| Поле | Куда попадает | Когда КЦ видит |
|---|---|---|
| `user_id`, `first_name`, `last_name`, `username` | схема `User`: `sender` у `message_created`, `user` у `bot_started` и `message_callback` | всегда |
| `phone` | только вложение `contact`: `vcf_phone`, `vcf_info` | по нажатию `request_contact` или отправке из чата |
| `latitude` / `longitude` | только вложение `location` | так же |
| `description` | **некуда** | никогда |

`description` в объём не входит. Контракт объявляет его в `UserWithPhoto`, а
`Message.sender` — это `User`. Единственные места с `UserWithPhoto` —
`GET /me` (там бот, не клиент) и `dialog_with_user` в `Chat`, а группа
`/chats` вне объёма мока. Аватары не входят по той же причине плюс отсутствие
внешних адресов в закрытом контуре.

## Находка: payload reply-кнопок ехать некуда

Контракт описывает **две разные** кнопки с типом `message`:

- inline `MessageButton` — наследует `Button`, у которого есть только `text`;
- reply `SendMessageButton` — наследует `ReplyButton`, у которого есть
  `payload` с описанием «Токен кнопки».

При этом `MessageBody` — тело, в котором событие `message_created` приезжает
на стенд — полей под этот payload не имеет вовсе. То есть объявленный «токен
кнопки» не имеет адресата в контракте: до бота доезжает только текст.

Следствие для КЦ: **нажатие `message`-кнопки неотличимо от того, что
пользователь набрал ту же строку руками** — ни у inline-, ни у
reply-клавиатуры. Кому нужна различимость, тому `callback` с `payload`.

Мок воспроизводит контракт: шлёт обычное `message_created` с текстом кнопки и
ничего не выдумывает. Расхождение фиксируется в README четвёртым пунктом
списка дефектов артефакта. Замер на живом Max — отдельная работа, как это
было с авторизацией; до замера утверждать, что так же ведёт себя прод, мы не
можем.

## Попутный дефект: contact от бота

`attachmentFromRequest` обрабатывает `contact` веткой `default` — то есть
кладёт payload запроса в сообщение как есть. Но формы разные:

- запрос (`ContactAttachmentRequestPayload`): `name`, `contact_id`,
  `vcf_info`, `vcf_phone`;
- сообщение (`ContactAttachmentPayload`): `vcf_info`, `hash`, `max_info`.

Валидация этого не ловит: обязательных полей у payload нет, а лишние схема
не запрещает. Стенд получает вложение, которого живой Max не пришлёт.
Чинится здесь же, потому что тот же код нужен для контакта от клиента.

## Дизайн

### Карточка клиента

`clients` получает четыре столбца: `last_name`, `phone`, `latitude`,
`longitude`. Миграция — как заведено, `ALTER TABLE` в списке `migrations`;
существующие базы переживают обновление без потери ботов и переписки.

```go
// ClientInput — данные для создания клиента.
type ClientInput struct {
    UserID    *int64   // задан — используется как есть, иначе генерируется
    FirstName string
    LastName  string
    Username  string
    Phone     string
    Latitude  *float64
    Longitude *float64
}

func (s *Store) CreateClient(botID int64, in ClientInput) (*Client, *Dialog, error)
```

Позиционные аргументы заменяются структурой: шесть подряд идущих строк —
приглашение перепутать местами имя с фамилией.

**Заданный `user_id`** — то, чего не хватало для связывания. Он и раньше был
стабилен (генерируется один раз, живёт в базе, одинаков во всех событиях), но
воспроизвести на моке конкретного абонента из тестовых данных КЦ было нельзя.
Занятый идентификатор отвергается новой ошибкой `ErrConflict` → `409` с кодом
`mock.conflict`: молча подсунуть другой `user_id` хуже, чем отказать.

`clientUser` начинает заполнять `last_name`.

### Кнопки

Живыми становятся четыре типа inline-клавиатуры и три reply-клавиатуры —
в reply у них другие имена, и это легко пропустить:

| Нажатие | Что уходит боту |
|---|---|
| `request_contact` / `user_contact` | `message_created` с единственным вложением `contact` |
| `request_geo_location` / `user_geo_location` | `message_created` с вложением `location` |
| `message` (обе клавиатуры) | обычное `message_created` с текстом кнопки |
| `clipboard` | ничего: текст копируется в буфер, как в Max |
| `callback`, `link` | как сейчас |
| `chat`, `open_app` | остаются с подсказкой «моком не обрабатывается» |

`chat` требует группы `/chats`, `open_app` — мини-приложения; обе вне объёма
мока, и делать вид, что они работают, вреднее, чем честно это показать.

Разбор типа кнопки живёт в веб-чате, а не в ядре: чат знает, какую кнопку
нажали, и вызывает подходящее действие control-API. Ядро получает три новых
действия клиента и не заводит диспетчера типов кнопок.

```go
func (c *Core) ClientSendContact(chatID int64) (*wire.Message, error)
func (c *Core) ClientSendLocation(chatID int64, lat, lon float64) (*wire.Message, error)
// текст кнопки уходит существующим ClientSendMessage
```

**Сборка вложения `contact`** — из карточки клиента:

- `vcf_phone` — телефон как есть;
- `vcf_info` — карточка VCARD 3.0 из имени, фамилии и телефона;
- `max_info` — тот же `User`, что и в `sender`, то есть в одном вложении
  приезжают и телефон, и `user_id`. Это и есть механизм связывания;
- `hash` — SHA-256 от телефона, усечённый до 32 символов. Контракт описывает
  его как признак «пользователь поделился номером, привязанным к аккаунту
  Max». Пустое поле означало бы «не привязан» и вводило бы КЦ в заблуждение;
  случайное значение ломало бы повторяемость тестов. Детерминированность от
  телефона даёт и то, и другое. Значение **не совпадает** с тем, что считает
  живой Max: алгоритм не опубликован. Это записывается в README, чтобы никто
  не начал сверять хеши со стендом.

Клиент без телефона на `request_contact` получает отказ `mock.validation` с
объяснением: контакт без номера бессмыслен, а тихо отправленное пустое
вложение выглядело бы как дефект КЦ.

Контракт требует, чтобы `contact` было **единственным** вложением сообщения;
мок это проверяет и отвечает `mock.validation`.

### Отправка без кнопки

Рядом со скрепкой в чате появляются две кнопки — контакт и геопозиция:
проверять обработку на стороне КЦ нужно и тогда, когда бот не просил, в Max
так можно. Геопозиция открывает поле с координатами из карточки, чтобы можно
было отправить не только точку по умолчанию.

### Форма создания клиента

`prompt('Имя клиента')` заменяется формой: имя, фамилия, username, телефон,
координаты, `user_id`. Все поля кроме имени необязательны и предзаполнены,
чтобы обычный сценарий остался в один клик.

## Тесты

| Уровень | Что проверяется |
|---|---|
| `store` | миграция старой базы без потери данных; сохранение и чтение новых полей; заданный `user_id` используется как есть; занятый — `ErrConflict` |
| `core` | `contact` собирается из карточки: телефон в `vcf_phone`, `user_id` в `max_info`, VCARD разбирается; клиент без телефона получает отказ; `contact` вторым вложением отвергается; `location` из карточки и из явных координат; contact от **бота** переводится из формы запроса в форму сообщения |
| `core` | каждое событие валидируется против `openapi.MaxBotWebhook.yaml` — как и все существующие |
| `controlapi` | новые поля и три новых действия; `409` на занятом `user_id` |
| сквозной | бот присылает клавиатуру с `request_contact` → клиент нажимает → на стенд приезжает `message_created`, в котором телефон и тот же `user_id`, что и в `sender` |
