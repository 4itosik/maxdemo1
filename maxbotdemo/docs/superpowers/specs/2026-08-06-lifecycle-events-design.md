# События жизненного цикла: bot_added, bot_stopped, message_edited

**Дата:** 2026-08-06 · **Затрагивает:** `internal/maxapi/models.go`,
`internal/bot/bot.go`, `cmd/bot/main.go`, `README.md`

## Задача

Бот подписан на три события — `message_created`, `message_callback`,
`bot_started` — и обрабатывает ровно их. Добавить ещё три:

| Событие | Когда приходит | Что бот делает |
|---|---|---|
| `bot_added` | бота добавили в чат или канал | приветствие в этот чат |
| `bot_stopped` | пользователь остановил бота в настройках | запись в лог |
| `message_edited` | пользователь отредактировал своё сообщение | «Вы исправили: …» |

Полный список типов — пятнадцать, он в описании объекта `Update`. Эти три
выбраны потому, что показывают жизненный цикл бота целиком: как его позвали,
как с ним расстались и что бывает с уже сказанным.

## Что мешает сегодня

**1. Список событий оторван от обработчиков.** Подписка собирается в
`cmd/bot/main.go:145`, а `switch` по типам — в `internal/bot/bot.go:97`. Два
места, которые обязаны совпадать, лежат в разных пакетах, и ничто не мешает им
разъехаться: подписка на необработанное событие даёт шум в логе, обработчик без
подписки не сработает ни разу.

**2. Подписка сверяется только по URL.** `syncSubscription`
(`cmd/bot/main.go:132`) считает подписку актуальной, если совпал адрес:

```go
if s.URL == cfg.WebhookURL {
	subscribed = true
	continue
}
...
if subscribed {
	return nil
}
```

Расширенный `updateTypes` до Max не доедет вовсе: запись с нужным URL уже есть,
и `POST` не отправляется. Новые события не пришли бы ни разу, причём молча.

**3. Ответ на нажатие кнопки — это правка сообщения.** `AnswerOnCallback` с
полем `Message` заменяет исходное сообщение (то самое, с кнопками, которое
отправил сам бот). Подписка на `message_edited` без защиты превращает каждое
нажатие в лишний ответ — разбор ниже.

## Решение

### Список событий переезжает в `internal/bot`

Рядом с `Commands()`, по тому же принципу: список — свойство поведения бота, а
`main.go` его только применяет.

```go
// UpdateTypes возвращает события, на которые бот подписывается. Список обязан
// совпадать с ветками Handle: подписка на необработанное событие даёт шум,
// обработчик без подписки не сработает ни разу.
func UpdateTypes() []string {
	return []string{
		maxapi.UpdateMessageCreated,
		maxapi.UpdateMessageCallback,
		maxapi.UpdateMessageEdited,
		maxapi.UpdateBotStarted,
		maxapi.UpdateBotStopped,
		maxapi.UpdateBotAdded,
	}
}
```

Три новые константы в `internal/maxapi/models.go` рядом с нынешними.

Новых полей в `Update` не требуется. `bot_added` приносит `chat_id`, `user` и
`is_channel`; первые два уже объявлены, а `is_channel` боту не нужен —
приветствие одинаковое и в группе, и в канале. В лог оно всё равно попадает:
`internal/webhook/server.go:86` пишет сырое тело каждого события целиком.

### Подписка: сверка набора и один `POST`

```go
func syncSubscription(ctx context.Context, api *maxapi.Client, cfg config) error {
	existing, err := api.GetSubscriptions(ctx)
	if err != nil {
		return fmt.Errorf("чтение подписок: %w", err)
	}

	want := bot.UpdateTypes()
	var current []string
	found := false
	for _, s := range existing {
		if s.URL == cfg.WebhookURL {
			current, found = s.UpdateTypes, true
			continue
		}
		if err := api.Unsubscribe(ctx, s.URL); err != nil {
			return fmt.Errorf("снятие устаревшей подписки %s: %w", s.URL, err)
		}
	}

	if found && sameSet(current, want) {
		return nil
	}
	if err := api.Subscribe(ctx, cfg.WebhookURL, cfg.Secret, want); err != nil {
		return fmt.Errorf("подписка на webhook %s: %w", cfg.WebhookURL, err)
	}
	return nil
}
```

Два решения тут неочевидны.

**Набор сравнивается как множество.** Порядок `update_types` в ответе
`GET /subscriptions` контрактом не оговорён, и полагаться на него нельзя.
`sameSet(a, b []string) bool` в `cmd/bot/main.go` рядом с `syncSubscription`.

**`DELETE` перед `POST` не делается.** Соблазн «пересоздать подписку» есть, но
между снятием и созданием остаётся окно, в котором события падают в никуда.
Документация метода говорит прямо: «Чтобы обновить подписку на события,
используйте `POST /subscriptions`» — дедупликация идёт по URL. Наблюдение из
README о том, что `POST` «добавляет ещё одну подписку», относится к *другому*
адресу: новый туннель — новый URL, отсюда и несколько записей. `max-mock`
подтверждает семантику: `AddSubscription` выполняет
`ON CONFLICT(bot_id, url) DO UPDATE SET update_types = excluded.update_types`.

Если живой Max поведёт себя иначе, это увидит первый же прогон по `.env.live`:
в `GET /subscriptions` окажутся две записи с одним URL. Проверка входит в живой
прогон; тогда — и только тогда — добавляется `DELETE`.

### `bot_added` — приветствие в чат

```go
func (b *Bot) sendChatGreeting(ctx context.Context, u maxapi.Update) {
	greeting := "Здравствуйте! Я демонстрационный бот Max."
	if name := u.Sender().DisplayName(); name != "" {
		greeting = fmt.Sprintf("Здравствуйте! Меня добавил %s. Я демонстрационный бот Max.", name)
	}
	b.send(ctx, u, maxapi.NewMessageBody{
		Text:        greeting + "\n\n" + helpText(),
		Attachments: []maxapi.AttachmentRequest{demoKeyboard().Attachment()},
	})
}
```

Адресат берётся существующим `Update.Target()` без правок: при `Message == nil`
он возвращает `Target{ChatID: u.ChatID, UserID: u.User.UserID}`, а `SendMessage`
предпочитает `chat_id` — то есть ответ уходит в чат, а не в личку добавившему.
`Sender()` в этом событии возвращает `u.User` — того, кто добавил.

В канале (`is_channel: true`) приветствие такое же. Отдельная ветка не делается:
сообщение бота в канале видят все подписчики, но демобот на то и демонстрационный
— он показывает событие, а не молчит о нём.

Клавиатура та же, что в личном приветствии. Кнопки `request_contact` и
`request_geo_location` в группе нажмёт любой участник и получит свой ответ — это
ровно то, что демобот и показывает. Команды в группах Max присылает с
идентификатором бота (`/help:id-773`); суффикс уже отбрасывает `Update.Command()`.

### `bot_stopped` — только лог

```go
// handleBotStopped фиксирует остановку в логе. Отправлять нечего: пользователь
// бота и остановил. Контекст обработчику не нужен — он никуда не ходит.
func (b *Bot) handleBotStopped(u maxapi.Update) {
	// Sender() возвращает указатель, и он бывает пустым: обращаться к полю
	// напрямую нельзя. DisplayName() от этого защищён, доступ к UserID — нет.
	var userID int64
	if s := u.Sender(); s != nil {
		userID = s.UserID
	}
	b.log.Info("пользователь остановил бота", "chat_id", u.ChatID, "user_id", userID)
}
```

Отправить нечего: пользователь бота и остановил — прощальное сообщение либо не
дойдёт, либо будет отклонено API. Состояния бот не хранит, чистить тоже нечего.
В этом и смысл строки: событие видно, а делать с ним демоботу нечего.

### `message_edited` — эхо правки с защитой от собственных правок

Наивная версия ломается о собственный ответ бота. `AnswerOnCallback` с полем
`Message` заменяет сообщение с кнопками — а его отправил бот. В `max-mock` это
буквально `AnswerCallback → applyEdit → publish(message_edited)`
(`internal/core/bot.go:206` и `:136`), и, в отличие от `appendMessage`, фильтра
«своё боту не присылать» там нет.

Без защиты:

```
клиент нажимает «Привет»
бот    заменяет сообщение на «Вы нажали: Привет»
мок    → message_edited, sender = сам бот (is_bot: true)
бот    «Вы исправили: Вы нажали: Привет»     ← мусор
```

Бесконечной петли нет — ответ на правку это новое сообщение, а не правка, — но
каждое нажатие кнопки начинает двоиться.

```go
func (b *Bot) handleEdit(ctx context.Context, u maxapi.Update) {
	// Собственные правки бота приходят обратно: POST /answers заменяет
	// сообщение с кнопками, и это порождает message_edited с sender = бот.
	// Без этой проверки каждое нажатие кнопки давало бы лишний ответ.
	if s := u.Sender(); s != nil && s.IsBot {
		return
	}
	if u.Text() == "" {
		// Правка вложения или снятие текста — отвечать нечем.
		return
	}
	b.send(ctx, u, maxapi.NewMessageBody{
		Text: fmt.Sprintf("Вы исправили: %s", u.Text()),
	})
}
```

Правок вложений бот не разбирает: `contact` и `location` осмысленно приходят
один раз, и повторять на правку разбор контакта незачем.

Команды при правке **не выполняются**: `/hepl` → `/help` даёт «Вы исправили:
/help», справка не присылается. Так событие видно отдельно от обычного эхо —
иначе правка была бы неотличима от нового сообщения, а показать нужно именно её.

`Target()`, `Sender()` и `Text()` работают без изменений: `message_edited`
приносит полный объект `Message` с `recipient` и `sender`.

### `Handle` целиком

```go
switch u.UpdateType {
case maxapi.UpdateBotStarted:
	b.sendGreeting(ctx, u)
case maxapi.UpdateBotAdded:
	b.sendChatGreeting(ctx, u)
case maxapi.UpdateBotStopped:
	b.handleBotStopped(u)
case maxapi.UpdateMessageCreated:
	b.handleMessage(ctx, u)
case maxapi.UpdateMessageEdited:
	b.handleEdit(ctx, u)
case maxapi.UpdateMessageCallback:
	b.handleCallback(ctx, u)
default:
	b.log.Debug("событие без обработчика", "update_type", u.UpdateType)
}
```

## Живая проверка

Покрывается не всё, и это существенно.

| Что проверяем | `max-mock` | Живой Max (`.env.live`) |
|---|---|---|
| `message_edited` | да — действие `edit` | да |
| собственная правка бота (`is_bot`) | да — действие `press` | да |
| `bot_stopped` | да — действие `stop` | да — остановить бота в его настройках |
| обновление подписки одним `POST` | да | да — сверить `GET /subscriptions` |
| `bot_added` | **нет** — групповых чатов у мока нет вовсе | да — добавить бота в группу |

Проверка идёт control-API мока (`POST /mock/api/dialogs/{chatId}/actions`), а не
кликами в веб-чате: тот же путь, которым ходит сам веб-чат, так что события
собираются настоящие, а прогон воспроизводим. Доступные действия: `start`,
`stop`, `send`, `send_contact`, `send_location`, `press`, `edit`, `delete`.

`bot_stopped` мок шлёт (`ClientStop`, `internal/core/client.go:81`), хотя его
README перечисляет только пять исходящих событий и `bot_stopped` в списке
пропущен — список устарел, код новее.

Не покрывается моком только `bot_added`: групповых чатов в нём нет, и событие
неоткуда взяться. До живого прогона оно стоит на юнит-тестах. Результаты живого
прогона дописываются в этот раздел, как это сделано в спеке контакта и
геопозиции.

### Результаты прогона

Прогон против `max-mock` (мок на `:8080`, бот на `:8081`, база мока
`../maxmoc/max-mock.db` — уже содержала бота `support_bot` с прошлой сессии,
токен в `.env` подошёл без переустановки). Бот подключён к диалогу через
`POST /mock/api/bots/{id}/clients`, дальше — control-API
`POST /mock/api/dialogs/{chatId}/actions` с действиями `start`, `send`, `edit`,
`press`, `stop`.

| Что проверялось | Результат |
|---|---|
| `POST /subscriptions` обновляет запись по URL | до старта бота в моке лежала одна старая подписка (3 типа, с прошлой задачи); после `register()` — по-прежнему **одна** запись с `http://localhost:8081/webhook`, но уже с шестью `update_types` (`message_created`, `message_callback`, `message_edited`, `bot_started`, `bot_stopped`, `bot_added`). Второй записи не появилось |
| `bot_started` | приветствие с клавиатурой из четырёх рядов пришло в диалог — стенд работает |
| `message_edited` от клиента | `send` → «Вы написали: Привет»; `edit` на тот же `mid` → в логе бота `update_type":"message_edited"` с `sender.is_bot=false` (клиент); ответ — «Вы исправили: Привет, бот» |
| собственная правка бота (`is_bot=true`) | `press` по кнопке «Привет» в приветствии заменил сообщение на «Вы нажали: Привет»; в логе бота следом пришло **второе** событие `message_edited` — на это же сообщение, `sender.is_bot":true`, текст уже «Вы нажали: Привет». Обработчик его пропустил: после этого события в логе только `POST /answers`, ни одного `POST /messages`. «Вы исправили: Вы нажали: Привет» не появилось |
| `bot_stopped` | `stop` → в логе строка `"пользователь остановил бота" chat_id=... user_id=...`; новых сообщений в диалоге не появилось |
| журнал доставок | 6 доставок этой сессии (`bot_started`, `message_created`, `message_edited`×2, `message_callback`, `bot_stopped`) — все со статусом `200`; в логе бота ни одного `ERROR`/`WARN`. В общем журнале (`GET /bots/{id}/deliveries`) есть и старые записи со статусом `0` — это доставки из прошлых сессий, когда бот не был поднят, к текущему прогону отношения не имеют |
| `bot_added` | **не проверялся** — групповых чатов у мока нет, эмулятор их не создаёт. Событие остаётся только на юнит-тестах задачи 1, ждёт живого Max (`.env.live`) |

Все три допущения, ради которых затевалась живая проверка, подтвердились
полностью и без правок кода:

1. `POST /subscriptions` действительно обновляет подписку по URL — `DELETE`
   перед ним не нужен, вторая запись не заводится.
2. Правка сообщения клиентом доезжает до бота событием `message_edited`.
3. Ответ бота на нажатие кнопки (`POST /answers`, подменяющий сообщение с
   клавиатурой) тоже возвращается боту событием `message_edited`, но с
   `sender.is_bot == true` — и обработчик из задачи 3 корректно его
   игнорирует, не отвечая на собственную правку.

Расхождений в поведении бота и проверяемых допущениях не найдено.

Прогон прошёл только против `max-mock`; `.env.live` в этой сессии не
поднимался. Колонка «Живой Max (`.env.live`)» в таблице выше не проверена
целиком — не только по строке `bot_added`, у которой это отмечено явно, но и
по остальным четырём. Больше того, допущение №1 из списка выше — про то, что
`POST /subscriptions` обновляет подписку по URL, а не плодит дубликаты, —
выведено из исходников мока (`ON CONFLICT(bot_id, url) DO UPDATE ...`, см. выше)
и тем же моком подтверждено: проверка замкнута сама на себя и ничего не
говорит о поведении живого Max. Если он ведёт себя иначе, это проявится первым
же прогоном по `.env.live` — двумя записями с одним URL в `GET /subscriptions`.

## Документация

В README:

- таблица «Что умеет» — три новые строки;
- абзац о том, что `POST /subscriptions` обновляет подписку по URL (а не плодит
  дубликаты) и потому старт сверяет не только адрес, но и набор событий; нынешнее
  описание подписки поправить — оно объясняет только случай нового адреса;
- в «Известные ограничения» — `bot_stopped` только логируется; `bot_added` моком
  не воспроизводится; правка сообщения не перезапускает команду.

## Что не делается

- **`dialog_removed`** — приходит вместе с `bot_stopped` и дал бы вторую запись
  об одном и том же событии.
- **`bot_removed`, `message_removed`, `user_added`, `user_removed`,
  `chat_title_changed`, `dialog_*`** — оставшиеся девять типов. Отдельная задача,
  если понадобятся.
- **`message_chat_created`** — схема в контракте есть, но в
  `discriminator.mapping` объекта `Update` её нет: строкового имени типа
  официально не задано, подписаться вслепую нельзя.
- **Хранение состояния диалога.** Бот его не имеет, и `bot_stopped` чистить
  нечего.
- **Ветка по `is_channel`.** Приветствие в канале и в группе одинаковое — так
  решено сознательно, поле остаётся видимым только в сыром логе события.
