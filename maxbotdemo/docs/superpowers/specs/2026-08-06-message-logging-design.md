# Полученное и отправленное сообщение в логе

**Дата:** 2026-08-06 · **Затрагивает:** `internal/jsonlog/jsonlog.go` (новый),
`internal/webhook/server.go`, `internal/maxapi/client.go`, `cmd/bot/main.go`,
`README.md`

## Задача

Видеть в логе содержимое переписки: что бот получил от Max и что отправил в
ответ. Весь лог при этом становится JSON — строка целиком разбирается `jq`, а
тела сообщений вкладываются в неё объектами.

## Что мешает сегодня

**1. Лог не показывает содержимое.** `webhook/server.go:71` пишет
`получено событие` с одним `update_type`; `bot.go:258` пишет `ответ отправлен`
с `chat_id` и `user_id`. Что было в сообщении — не видно ни там, ни там.

**2. Тела нигде не задерживаются.** Входящее тело читается декодером прямо из
`r.Body` (`webhook/server.go:64`) и после разбора недоступно. Исходящее тело
маршалится в локальную переменную `encoded` внутри `Client.do`
(`maxapi/client.go:89`), ответ API — в `raw` (`client.go:111`); наружу не
выходит ни то, ни другое.

**3. Текстовый формат не даёт вложить JSON.** `main.go:29` создаёт
`slog.NewTextHandler`. Даже с готовым телом на руках он выдал бы
`payload="{\"text\":\"привет\"}"` — экранированную строку, которую не разобрать
одним проходом.

## Решение

### Сырой JSON внутри лога — `internal/jsonlog`

Ключевая деталь: `slog.JSONHandler` кодирует значение `slog.Any` через
`json.Marshal`. Значит, тип с методом `MarshalJSON`, возвращающим тело как
есть, попадает в лог объектом, а не строкой.

```go
// Package jsonlog кладёт сырой JSON в лог так, чтобы он остался JSON'ом.
package jsonlog

// Raw — сырое тело запроса или ответа для slog.Any.
type Raw []byte

func (r Raw) MarshalJSON() ([]byte, error)
```

Пакет отдельный, потому что тип нужен двум пакетам сразу — `webhook` и
`maxapi`, — а к предмету ни одного из них не относится.

Три случая, и все три обязаны дать валидный JSON: строка лога не должна
ломаться из-за того, что в неё попало.

| Что на входе | Что в логе | Зачем |
|---|---|---|
| валидный JSON | вкладывается как есть | ради этого всё и делается |
| не JSON | JSON-строка с тем же текстом | мусор от чужого запроса не должен ломать строку лога |
| пусто (`nil`) | `null` | у `GET /me` и `DELETE /subscriptions` тела нет |

Валидность проверяется `json.Valid` на каждой записи. Для демобота это дёшево.

### Формат вывода — `cmd/bot/main.go`

`slog.NewTextHandler` → `slog.NewJSONHandler`. Уровень остаётся `Info`, новых
переменных окружения не появляется.

### Входящее — `internal/webhook/server.go`

Тело читается в память, а не разбирается из потока:

```go
raw, err := io.ReadAll(http.MaxBytesReader(w, r.Body, maxBodyBytes))
...
err = json.Unmarshal(raw, &u)
```

Лимит `maxBodyBytes = 1 << 20` — прямое следствие буферизации: пока тело
читалось декодером, класть его целиком в память никто не обещал.

На каждый принятый запрос — по-прежнему ровно одна строка лога, `payload` есть
в обеих ветках:

```json
{"level":"INFO","msg":"получено событие","update_type":"message_created","payload":{…}}
{"level":"WARN","msg":"не удалось разобрать событие","error":"…","payload":"…"}
```

Ошибка чтения тела — третья ветка, `400`, как и ошибка разбора.

Запрос с неверным секретом отклоняется до чтения тела, поэтому в лог оно не
попадает.

### Исходящее — `internal/maxapi/client.go`

У клиента появляется логгер:

```go
// WithLogger включает запись запросов и ответов API в лог.
func WithLogger(log *slog.Logger) Option
```

По умолчанию — `slog.New(slog.DiscardHandler)`. Молчание, а не `nil`: так
`do` не обрастает проверками, а нынешние тесты клиента продолжают работать без
правок. `main.go` передаёт общий логгер в обеих ветках `newAPIClient`.

В `do` — две записи на запрос:

```json
{"msg":"запрос к API","method":"POST","path":"/messages","query":"chat_id=42","payload":{"text":"Вы написали: привет"}}
{"msg":"ответ API","method":"POST","path":"/messages","status":200,"payload":{"message":{…}}}
```

Запись «ответ API» делается и при `4xx`/`5xx` — до превращения тела в
`*APIError`: причина отказа видна целиком, а не только в свёрнутом виде
`max api: 400 …`. При сетевой ошибке ответа нет, и вторая запись не делается —
ошибка возвращается вызывающему, как и сейчас.

Заголовки не логируются, поэтому токен из `Authorization` в лог не попадает.

`internal/bot` не меняется вовсе: его записи «ответ отправлен» и «ответ на
нажатие кнопки отправлен» остаются как есть и говорят об исходе, а содержимое
теперь видно строкой выше — дублировать его в двух местах незачем.

**Маскирование.** Тело `POST /subscriptions` содержит `secret` — по смыслу
пароль. Функция `redact` разбирает тело в `map[string]json.RawMessage`,
подменяет `secret` на `"***"` и собирает обратно; тело без этого поля
возвращается неизменным, неразбираемое — тоже. Применяется и к запросу, и к
ответу: чужой контракт менять не нам, и если `secret` однажды появится в ответе
`GET /subscriptions`, маскирование уже на месте.

**Что не маскируется:** телефон и координаты из вложений. Увидеть их в логе —
ровно то, ради чего задача и делается. В README это отмечается прямо: лог
демобота содержит персональные данные.

## Тесты

| Что | Где | Случаи |
|---|---|---|
| `jsonlog.Raw` | `internal/jsonlog/jsonlog_test.go` | валидный JSON вкладывается объектом; не-JSON становится строкой; `nil` даёт `null`; в каждом случае строка лога разбирается обратно |
| приём события | `internal/webhook/server_test.go` | `payload` в записи «получено событие» совпадает с отправленным телом; неразбираемое тело → `payload` строкой в записи-предупреждении; тело сверх лимита → `400` |
| запросы клиента | `internal/maxapi/client_test.go` | `SendMessage` пишет и запрос, и ответ; `query` содержит `chat_id`; ответ `4xx` тоже логируется; запрос без тела даёт `payload:null` |
| маскирование | `internal/maxapi/client_test.go` | `secret` из `POST /subscriptions` в логе заменён на `***`, `url` и `update_types` на месте |

Сеть не нужна: клиент проверяется на `httptest`-заглушке, как и сейчас.
Логгер во всех тестах — `slog.NewJSONHandler` в `bytes.Buffer`, записи
разбираются обратно `json.Unmarshal`: проверять подстроками то, ради чего
затевался машиночитаемый формат, было бы странно.

## Что не делается

- **Переменная `LOG_LEVEL` и уровень `Debug` для payload.** Бот
  демонстрационный: переписка нужна сразу и без настройки.
- **Ротация и запись в файл.** Лог идёт в `stderr`; перенаправление — дело
  того, кто запускает.
- **Логирование заголовков.** В них токен и секрет, а пользы для разбора
  переписки нет.
- **Идентификатор запроса, сшивающий «запрос к API» с «ответ API».** Записи
  идут парой подряд; при 32 одновременных обработчиках пары могут
  перемежаться, и если это начнёт мешать — тогда и добавим.
