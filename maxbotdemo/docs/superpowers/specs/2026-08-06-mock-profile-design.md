# Профиль запуска против max-mock

**Дата:** 2026-08-06 · **Затрагивает:** `cmd/bot/config.go`,
`internal/maxapi`, `README.md`, `.env.mock`

## Задача

Гонять бота против локального эмулятора
[`max-mock`](../../../../maxmoc/README.md) вместо живого Max: без туннеля, без
сертификата Минцифры, без модерации бота. Веб-чат мока играет роль клиента
мессенджера, вкладки «Журнал» и «Доставки» показывают обе стороны обмена.

Мок слушает `:8080` и отдаёт поверхность Bot API в корне, поэтому переезд —
это `MAX_API_BASE_URL=http://localhost:8080`.

## Что мешает сегодня

**1. Авторизация.** ~~Мок требовал `Bearer <token>` и отвечал `401`~~ —
починено на стороне мока по
[ТЗ](../../../../maxmoc/docs/specs/2026-08-06-auth-parity-tz.md): он принимает
`Authorization: <token>`, как живой Max. Здесь не менялось ничего — клиент API
был прав.

**2. Требование HTTPS в адресе webhook.** `webhookPath` (`cmd/bot/config.go:81`)
и `maxapi.Subscribe` (`internal/maxapi/subscriptions.go:27`) отвергают
`http://`. Живой Max действительно доставляет события только по HTTPS на 443,
но мок специально принимает `http://` — иначе он неприменим в закрытом контуре.

**3. Порт.** Мок уже занял `:8080` — дефолт `LISTEN_ADDR` бота.

## Решение

### Правило адреса webhook

`http://` разрешается **только для петлевого хоста** — `localhost`, `127.0.0.1`,
`::1`. Всё остальное по-прежнему обязано быть `https://`.

Петлевое исключение выбрано вместо переменной окружения (`ALLOW_INSECURE_WEBHOOK=1`):
защита от случайной подписки живого Max на `http://`-адрес остаётся на месте
без единой новой ручки в конфиге, а обойти её нечаянно нельзя — петлевой адрес
недостижим ни для чего, кроме локального мока.

Ограничение осознанное: мок, поднятый на отдельной машине закрытого контура,
под правило не подпадёт. Такой сценарий тут не требуется; когда потребуется,
правило расширится до частных диапазонов или до явного флага — и это будет
отдельное решение с отдельным обоснованием.

Правило живёт в одном месте — новом файле `internal/maxapi/webhookurl.go`:

```go
// CheckWebhookURL проверяет, годится ли адрес для подписки на события.
func CheckWebhookURL(raw string) error
```

Оба нынешних сторожа зовут её: `webhookPath` — перед тем как вернуть путь,
`Subscribe` — вместо своей проверки префикса. Так формулировка «почему этот
адрес не годится» существует в единственном экземпляре и не разъедется.

### Профиль запуска

`.env` — активный профиль, и в нём лежит мок; боевой токен переехал в
`.env.live`, чтобы не потеряться. Переключение между стендами — копирование
нужного файла в `.env`. В `.gitignore` попадает `.env` и всё `.env.*`.

```sh
MAX_BOT_TOKEN=bot.…                    # выдаёт мок при регистрации бота
MAX_API_BASE_URL=http://localhost:8080
WEBHOOK_URL=http://localhost:8081/webhook
LISTEN_ADDR=:8081
WEBHOOK_SECRET=mock-secret-123
```

`MAX_API_CA_FILE` не задаётся: сертификат Минцифры нужен только для
`platform-api2.max.ru`.

## Что при этом не меняется

Логика бота, webhook-сервер, схема подписок. Мок отдаёт те же пути и те же
события, поэтому `syncSubscription` работает как есть: читает
`GET /subscriptions`, снимает чужие адреса, подписывается на свой.

## Что вскрылось при живой проверке

Два расхождения, которых не было видно на живом Max. Оба чинились по правилу
«исправляем того, кто неправ», а не того, кого проще править.

**1. Тело `POST /messages` не проходило по контракту.** `NewMessageBody`
объявляет `text`, `attachments` и `link` обязательными (и при этом nullable);
бот опускал пустые. Живой Max такое тело принимает, мок — валидирует по
контракту и отвечал `400 mock.validation`. Прав здесь мок: контракт есть
контракт. Поля в `NewMessageBody` (`internal/maxapi/models.go`) потеряли
`omitempty`, добавился тип `NewMessageLink`, и незаполненные уходят как `null`.

**2. Мок возвращал боту его же сообщения.** `message_created` рассылался всем
подписчикам независимо от отправителя, поэтому эхо-ответ бота приходил ему
самому — и порождал новое эхо. Бесконечная петля на первом же `/start`. Живой
Max собственные сообщения боту не шлёт (сквозной сценарий из коммита `3841a14`
прошёл без петли), так что прав бот. Починено в моке:
`core.appendMessage` публикует событие в UI всегда, а в webhook — только для
сообщений клиента.

## Тесты

Сеть по-прежнему не нужна.

| Что | Где | Случаи |
|---|---|---|
| `CheckWebhookURL` | `internal/maxapi/webhookurl_test.go` | `https://example.com/webhook` → ок; `http://localhost:8081/webhook` → ок; `http://127.0.0.1:8081/webhook` → ок; `http://[::1]:8081/webhook` → ок; `http://example.com/webhook` → ошибка; `ftp://…` → ошибка |
| `loadConfig` | `cmd/bot/config_test.go` | `http://localhost:8081/webhook` принимается, `WebhookPath` = `/webhook`; `http://example.com/webhook` отвергается |
| `Subscribe` | `internal/maxapi/client_test.go` | подписка на петлевой `http://` уходит на сервер, а не падает до запроса; на внешний `http://` — не уходит |
| `SendMessage` | `internal/maxapi/client_test.go` | тело содержит `text`, `attachments` и `link` даже когда вложений и ссылки нет |
| Петля событий | `maxmoc: internal/core/core_test.go` | сообщение бота не уходит в webhook, но приходит в веб-чат; сообщение клиента уходит в webhook |

**Живая проверка пройдена** (мок 0.0.32 на `:8080`, бот на `:8081`): нажатие
«Начать» дало приветствие с клавиатурой, `/help` — список команд, `/buttons` —
клавиатуру, произвольный текст — эхо, нажатие «Привет» — замену сообщения на
«Вы нажали: Привет». Все доставки — `200`, в логе бота ни одной ошибки.

**Проверка на живом Max тоже пройдена** — тем же кодом, через туннель
`cloudflared`: бот подписался (сняв устаревший адрес), ответил на сообщение и
на нажатие кнопки, ошибок в логе нет. Важно, что ответ на кнопку уходит телом
без вложений — то есть с `attachments: null` и `link: null`: прод принимает
контрактную форму так же, как принимал прежнюю сокращённую.
