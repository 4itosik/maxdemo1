# Контакт и геопозиция клиента

**Дата:** 2026-08-06 · **Затрагивает:** `internal/maxapi/models.go`,
`internal/maxapi/vcard.go` (новый), `internal/bot/bot.go`,
`internal/bot/keyboard.go`, `README.md`

## Задача

Научить бота просить у клиента номер телефона и геопозицию — и разбирать то,
что приходит в ответ.

Ни телефона, ни координат в схеме `User` нет: до бота они доезжают
исключительно вложениями `contact` и `location`. Кнопки `request_contact` и
`request_geo_location` заставляют клиент прислать **новое `message_created`** с
таким вложением — отдельного типа события у них нет, и `message_callback` при
нажатии не приходит.

## Что мешает сегодня

**1. Сообщение без текста отбрасывается.** `handleMessage`
(`internal/bot/bot.go:93`) выходит первой же строкой при пустом `Text()`. У
сообщения с контактом или геопозицией текста нет вовсе (`text: null`), поэтому
оно пропадает молча — до обработчика дело не доходит.

**2. `Attachment.Payload` типизирован клавиатурой.** `internal/maxapi/models.go:185`
объявляет `Payload *KeyboardPayload`. Payload контакта
`{vcf_info, hash, max_info}` разбирается в него без ошибки — просто
`Buttons == nil`, — так что номер недостижим и сбоя при этом никто не увидит.

**3. Нет нужных типов кнопок.** `internal/maxapi/models.go:196` знает только
`callback` и `link`.

## Решение

### Разделение входящего и исходящего вложения

Контракт различает две схемы, и совмещать их дальше нельзя: у исходящей
клавиатуры payload — массив кнопок, у входящего контакта — `vcf_info`,
`hash`, `max_info`.

| Схема контракта | Где встречается | Что кладём мы |
|---|---|---|
| `AttachmentRequest` | `NewMessageBody.attachments` — наш `POST /messages` | inline-клавиатура |
| `Attachment` | `MessageBody.attachments` — полученное сообщение | `contact`, `location` |

Нынешний `Attachment` — это по контракту `AttachmentRequest`, поэтому он
переименовывается, а имя `Attachment` достаётся входящему. Тип назван в пяти
местах: `internal/bot/keyboard.go` (сигнатура и литерал),
`internal/bot/bot.go` (два вызова), `internal/maxapi/client_test.go`.
`internal/bot/bot_test.go` обращается к полям, а не к типу, и правки не требует.

Метод `Keyboard.Attachment()` имя сохраняет: оно описывает действие —
превратить клавиатуру во вложение, — а схему контракта называет тип в
сигнатуре.

```go
// AttachmentRequest — вложение исходящего сообщения.
type AttachmentRequest struct {
	Type    string           `json:"type"`
	Payload *KeyboardPayload `json:"payload,omitempty"`
}

// Attachment — вложение полученного сообщения. Бот читает только contact и
// location, поэтому типизирован payload контакта; payload прочих типов
// разбирается в него вхолостую и остаётся пустым.
type Attachment struct {
	Type      string          `json:"type"`
	Payload   *ContactPayload `json:"payload,omitempty"`
	Latitude  *float64        `json:"latitude,omitempty"`
	Longitude *float64        `json:"longitude,omitempty"`
}

// ContactPayload — содержимое вложения contact.
type ContactPayload struct {
	VcfInfo string `json:"vcf_info,omitempty"`
	Hash    string `json:"hash,omitempty"`
	MaxInfo *User  `json:"max_info,omitempty"`
}
```

Два решения тут неочевидны.

**Payload типизирован, а не `json.RawMessage`.** Отложенный разбор дал бы
гибкость, которой демоботу некуда деться: он читает ровно два вложения, а
`RawMessage` протащил бы шаг декодирования в каждое место чтения. Цена —
типизацию придётся менять, если однажды понадобится payload картинки или
стикера.

**Координаты — указатели.** `0,0` — валидные координаты (Гвинейский залив), и
отличить их от «поля в JSON не было» иначе нечем.

### Аксессоры на `Update`

Рядом с нынешними `Text()` и `Command()`:

```go
// Location — координаты из вложения location.
type Location struct {
	Latitude  float64
	Longitude float64
}

func (u Update) Contact() *ContactPayload
func (u Update) Location() *Location
```

Оба ищут первое вложение подходящего типа. Контракт требует, чтобы `contact`
был единственным вложением сообщения, но бот на это не полагается: чужое
требование — не гарантия. `Location()` возвращает `nil`, если координат во
вложении нет.

### Разбор VCARD — `internal/maxapi/vcard.go`

```go
// Phone возвращает первый номер телефона из vcf_info.
func (p *ContactPayload) Phone() string

// Name возвращает имя контакта: FN из vcf_info, иначе имя из max_info.
func (p *ContactPayload) Name() string
```

Мок отдаёт стерильный VCARD 3.0 в четыре строки, живой Max — карточку с
телефона пользователя. Поэтому разбор учитывает:

| Особенность | Пример |
|---|---|
| параметры свойства | `TEL;TYPE=CELL:+79991234567` |
| групповой префикс (стиль Apple) | `item1.TEL;type=CELL:+79991234567` |
| свёрнутая строка (RFC 6350): продолжение начинается с пробела или табуляции | `FN:Иван\r\n Петров` |
| регистр имени свойства | `tel:`, `Tel:` |
| разделители строк | `\r\n` и `\n` |

Не делается: экранирование значений (`\,`, `\;`, `\\`) не разворачивается — в
телефоне и имени оно не встречается. Параметр в кавычках с двоеточием внутри
(`TEL;TYPE="a:b":+7…`) разбор сломает; контракт такого не порождает, и это
отмечено комментарием в коде, а не обойдено.

### Кнопки

```go
const (
	ButtonRequestContact     = "request_contact"
	ButtonRequestGeoLocation = "request_geo_location"
)

func RequestContactButton(text string) maxapi.Button
func RequestGeoLocationButton(text string) maxapi.Button
```

У обеих по контракту только `type` и `text`. У `request_geo_location` есть ещё
`quick` — отправка без запроса подтверждения; поле не добавляется, потому что
бот им не пользуется, а поведение по умолчанию (спросить подтверждение) ближе к
живому.

### Команды и клавиатуры

Две новые команды в `Commands()`. И в меню Max, и в `/help` они попадут сами:
`helpText()` собирается из того же списка.

| Команда | Описание в меню | Ответ бота | Кнопка |
|---|---|---|---|
| `/phone` | Прислать свой номер телефона | «Нажмите кнопку, чтобы поделиться номером телефона.» | «Поделиться номером» |
| `/location` | Прислать свою геопозицию | «Нажмите кнопку, чтобы отправить свою геопозицию.» | «Отправить геопозицию» |

Подписи кнопок живут в константах: они нужны и здесь, и в демо-клавиатуре, и
расходиться им незачем. Те же кнопки добавляются в
`demoKeyboard()` — то есть видны в приветствии (`bot_started`, `/start`) и по
`/buttons`:

```
┌───────────┬───────────┐
│ Привет    │  Пока     │  callback
├───────────┴───────────┤
│ Поделиться номером    │  request_contact
├───────────────────────┤
│ Отправить геопозицию  │  request_geo_location
├───────────────────────┤
│ Документация          │  link
└───────────────────────┘
```

Каждая новая кнопка занимает свой ряд: Max рекомендует не длиннее 10 символов
на подпись при двух кнопках в ряду, а обе длиннее.

### Обработка

В `handleMessage` вложения проверяются до текста:

```go
if c := u.Contact(); c != nil {
	b.handleContact(ctx, u, c)
	return
}
if l := u.Location(); l != nil {
	b.handleLocation(ctx, u, l)
	return
}
if u.Text() == "" {
	return
}
```

Побочно это бесплатно покрывает контакт и геопозицию, присланные из чата без
всякой кнопки бота — в веб-чате мока это кнопки 👤 и 📍 рядом со скрепкой.

Ответы собираются построчно, отсутствующие строки пропускаются:

```
Спасибо! Вот что пришло:
Телефон: +79991234567
Имя: Иван Петров
user_id: 1042
Номер привязан к аккаунту Max: да
```

```
Спасибо! Вот что пришло:
Широта: 55.751244
Долгота: 37.618423
```

Координаты печатаются через `strconv.FormatFloat(v, 'f', -1, 64)`: `%v` дал бы
`1e-07` вместо `0.0000001`.

Вырожденные случаи:

| Что пришло | Ответ |
|---|---|
| контакт без номера | «Контакт пришёл, но номера телефона в нём нет.» — даже если имя и `user_id` на месте: номер здесь и есть предмет |
| контакт без `max_info` | строки `user_id` нет, остальные на месте |
| контакт без `FN` в `vcf_info` | имя берётся из `max_info` |
| вложение `location` без координат | игнорируется: `Location()` вернёт `nil`, дальше сработает проверка пустого текста |

Строка «Номер привязан к аккаунту Max» требует оговорки. Контракт описывает
`hash` как признак того, что клиент поделился номером своего аккаунта, но
алгоритм живой Max не публикует — сверить значение не с чем. Бот докладывает
только наличие непустого поля; это **не** проверка, и так это и будет описано в
README. Мок считает `hash` как SHA-256 от телефона, и его значение со стендом
несравнимо.

| демо-клавиатура | `internal/bot/bot_test.go` | обе новые кнопки на месте, ряды в ожидаемом порядке |
| приём контакта | `internal/bot/bot_test.go` | номер, имя и `user_id` в ответе; контакт без номера → отбойник; контакт без `max_info` → ответ без строки `user_id` |
| приём геопозиции | `internal/bot/bot_test.go` | широта и долгота в ответе |
| `/help` | `internal/bot/bot_test.go` | новые команды в справке — следствие того, что она собирается из `Commands()` |

Сеть не нужна: `Sender` подставной, как и во всех нынешних тестах бота.

**Живая проверка пройдена** против `max-mock` (мок на `:8080`, бот на `:8081`).
Юнит-тесты кормят бота теми же структурами, которые сами и придумали, — а вся
конструкция стоит на допущении о том, что пришлёт клиент по нажатию кнопки.
Проверить это допущение может только мок или живой Max.

Проверка шла не кликами в веб-чате, а через control-API мока
(`POST /mock/api/dialogs/{chatId}/actions` с действиями `send_contact`,
`send_location`, `send`) — тот же путь, которым ходит сам веб-чат, так что
вложение собирается настоящее, а прогон воспроизводим:

| Что проверялось | Результат |
|---|---|
| публикация команд при старте | в моке пять команд, включая `phone` и `location` |
| приветствие (`bot_started`) | клавиатура из четырёх рядов; кнопки-запросы каждая в своём ряду |
| `/phone` | сообщение с единственной кнопкой `request_contact` |
| нажатие → вложение `contact` | сообщение **без текста**, `vcf_info` с `TEL;TYPE=CELL:+79991234567`, непустой `hash`, `max_info` с `user_id` |
| ответ на контакт | телефон, имя, `user_id` и «Номер привязан к аккаунту Max: да» |
| `/location` | сообщение с единственной кнопкой `request_geo_location` |
| нажатие → вложение `location` | координаты на верхнем уровне вложения, не в `payload` |
| ответ на геопозицию | `Широта: 55.751244`, `Долгота: 37.618423` — подписи не перепутаны |
| контакт без кнопки бота | тот же ответ: обработчик один и тот же |
| доставки | 12 из 12 — `200`; в логе бота ни ошибки, ни предупреждения |

Допущение подтвердилось полностью: ответ на кнопку приходит обычным
`message_created` без текста, и без перестановки проверок в `handleMessage`
он терялся бы молча.

Не проверено через мок: вырожденный случай «контакт без номера». Мок отвечает
`400` («контакт без номера бессмыслен») и такого вложения не порождает вовсе,
поэтому этот путь закрыт только юнит-тестом.

## Документация

В README:

- таблица «Что умеет» — строки `/phone`, `/location` и «пользователь поделился
  контактом или геопозицией»;
- отдельный абзац о том, что телефона и координат в схеме `User` нет и они
  приезжают только вложениями — это неочевидно и объясняет форму решения;
- в «Известные ограничения» — что `hash` не проверяется, что `quick` у кнопки
  геопозиции не используется и что экранирование VCARD не разворачивается.

## Что не делается

- **Хранение номера.** Бот без состояния; ответ «Спасибо, записал» был бы
  неправдой.
- **Отправка контакта и геопозиции самим ботом** (`ContactAttachmentRequest`,
  `LocationAttachmentRequest`) — обратное направление, отдельная задача.
- **Reply-клавиатура** (`user_contact`, `user_geo_location`) — другой тип
  клавиатуры со своим билдером; inline покрывает сценарий целиком.
