# maxbotdemo

Демонстрационный бот для мессенджера [MAX](https://max.ru) на Go.
Отвечает на команды, показывает inline-клавиатуру, обрабатывает нажатия кнопок,
принимает контакт и геопозицию. События получает через webhook.

Только стандартная библиотека Go — никаких внешних зависимостей.

## Что умеет

| Событие | Ответ бота |
|---|---|
| Пользователь нажал «Начать» (`bot_started`) | приветствие по имени + клавиатура |
| Бота добавили в чат или канал (`bot_added`) | приветствие в этот чат с именем добавившего |
| Пользователь остановил бота (`bot_stopped`) | только запись в лог — отправлять уже некуда |
| `/start` | то же самое |
| `/help` | список команд |
| `/buttons` | сообщение с кнопками |
| `/phone` | сообщение с кнопкой «Поделиться номером» |
| `/location` | сообщение с кнопкой «Отправить геопозицию» |
| нажатие кнопки (`message_callback`) | «Вы нажали: `подпись кнопки`» вместо исходного сообщения |
| пользователь поделился контактом или геопозицией | разбор вложения: телефон, имя, `user_id` — или координаты |
| пользователь отредактировал своё сообщение (`message_edited`) | «Вы исправили: …»; команда при этом не выполняется |
| любой другой текст | эхо: «Вы написали: …» |

Телефона и координат в схеме `User` нет вовсе — до бота они доезжают только
вложениями `contact` и `location`. Кнопки `request_contact` и
`request_geo_location` отдельного события не порождают: по нажатию клиент
присылает обычное `message_created` с таким вложением и **без текста**. Отсюда
две вещи в коде: `handleMessage` смотрит вложения раньше текста, а телефон
достаётся разбором строки `TEL` из карточки VCARD (`internal/maxapi/vcard.go`).

Тем же обработчиком покрыт контакт, отправленный из чата скрепкой, без всякой
кнопки от бота.

## Структура

```
cmd/bot/            запуск: конфиг, регистрация, HTTP-сервер, остановка
internal/maxapi/    клиент Max Bot API: модели, запросы, ошибки
internal/bot/       логика бота — не знает про HTTP, тестируется без сети
internal/webhook/   приём событий по HTTP: проверка секрета, разбор, диспетчеризация
```

Логика бота зависит от узкого интерфейса `bot.Sender`, а не от клиента целиком —
поэтому все сценарии из таблицы выше покрыты тестами без единого сетевого вызова.

## Что нужно перед запуском

**1. Токен бота.** Авторизуйтесь на [business.max.ru](https://business.max.ru),
создайте бота и получите токен в разделе «Интеграция» после модерации.

**2. Корневой сертификат Минцифры.** Домен `platform-api2.max.ru` подписан
цепочкой «Russian Trusted Root CA», которой нет в системном наборе macOS и
большинства Linux-образов. Без неё любое обращение к API падает с
`x509: certificate signed by unknown authority`.

Проверить, нужен ли сертификат:

```sh
curl -sS -o /dev/null -w '%{http_code}\n' https://platform-api2.max.ru/me
# 401 — сертификат уже доверенный, всё в порядке
# ошибка SSL certificate problem — нужен корневой сертификат
```

Если нужен — скачайте его и укажите путь в `MAX_API_CA_FILE`. Системное
хранилище при этом не меняется: сертификат подключается только к этой программе
(см. `internal/maxapi/tls.go`).

```sh
mkdir -p certs
curl -o certs/russian_trusted_root_ca.cer https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer
```

**3. Публичный HTTPS-адрес.** MAX доставляет события только по HTTPS на порт 443
и только на сертификат доверенного УЦ. Для локальной разработки подойдёт туннель:

```sh
brew install cloudflared
cloudflared tunnel --protocol http2 --url http://localhost:8080
# выведет адрес вида https://xxxx-yyyy.trycloudflare.com
```

`--protocol http2` нужен, если исходящий UDP закрыт (частый случай под VPN и в
корпоративных сетях). По умолчанию `cloudflared` ходит через QUIC поверх UDP, и
при закрытом UDP туннель **молча не поднимается**: адрес выдаётся, MAX принимает
на него подписку, но события никуда не доходят. Признак — в логе туннеля
`Failed to dial a quic connection` и ни одной строки
`Registered tunnel connection`.

## Запуск

```sh
export MAX_BOT_TOKEN='ваш-токен'
export WEBHOOK_URL='https://xxxx-yyyy.trycloudflare.com/webhook'
export WEBHOOK_SECRET='dev-secret-123'
export MAX_API_CA_FILE='certs/russian_trusted_root_ca.cer'   # если нужен

go run ./cmd/bot
```

Бот при старте проверит токен (`GET /me`), опубликует команды
(`PATCH /me/commands`) и настроит подписку.

Настройка подписки — не просто `POST /subscriptions`. Подписка опознаётся по
URL: повторный `POST` на тот же адрес обновляет её, а на другой — заводит
вторую. После пары запусков с разными адресами (новый туннель — новый адрес)
MAX начинает слать каждое событие на все подписки сразу. Поэтому бот сначала
читает `GET /subscriptions` и снимает чужие адреса.

Свой адрес он сверяет и по набору событий: список живёт в `bot.UpdateTypes()`
рядом с обработчиками, и стоит ему измениться — подписка обновляется одним
`POST`. Без этой сверки новые события не пришли бы ни разу, причём молча:
запись с нужным адресом уже есть. `DELETE` перед `POST` не делается — он
открыл бы окно, в котором события падают в никуда. Посмотреть текущее
состояние:

```sh
curl -H "Authorization: $MAX_BOT_TOKEN" \
     --cacert certs/russian_trusted_root_ca.cer \
     https://platform-api2.max.ru/subscriptions
```

## Запуск против max-mock

[`max-mock`](../maxmoc/README.md) — локальный эмулятор Max: он отдаёт ту же
поверхность Bot API и веб-чат `/mock/chat/{botId}`, где вы играете роль
клиента. Ни туннель, ни сертификат Минцифры, ни модерация бота при этом не
нужны — мок живёт целиком на localhost.

Профиль отличается от боевого тремя строками: базовый адрес API, петлевой
webhook по HTTP и свой порт (`:8080` уже занял мок).

```sh
cd ../maxmoc && ./max-mock            # мок слушает :8080

# бот в соседнем терминале
set -a && . ./.env && set +a
go run ./cmd/bot
```

`.env` — активный профиль, и сейчас в нём лежит именно мок; боевой хранится
рядом, в `.env.live`, и читается напрямую (см. «Запуск против живого Max»).
Оба файла в git не попадают.

```sh
MAX_BOT_TOKEN=bot.…                    # выдаёт мок при регистрации бота
MAX_API_BASE_URL=http://localhost:8080
WEBHOOK_URL=http://localhost:8081/webhook
LISTEN_ADDR=:8081
WEBHOOK_SECRET=mock-secret-123
```

Бота заводят в админке мока `http://localhost:8080/mock` — она же показывает
вкладки «Журнал» и «Доставки» с обеими сторонами обмена. Дальше всё как с
живым Max: бот проверит токен, опубликует команды и подпишется на события.

`http://` в `WEBHOOK_URL` разрешён **только** для петлевого хоста
(`localhost`, `127.0.0.1`, `::1`) — правило живёт в `maxapi.CheckWebhookURL`.
Подписать живой Max на `http://`-адрес по-прежнему нельзя, а до петлевого
адреса он всё равно не дотянется.

## Запуск против живого Max

`.env.live` — боевой профиль: токен с business.max.ru, корневой сертификат
Минцифры и `LISTEN_ADDR=:8090`. Порт свой, не `:8080` и не `:8081`, поэтому
живой бот поднимается рядом с моком и мок-ботом — все трое работают
одновременно, и копировать `.env.live` в `.env` не нужно.

Нужны два терминала: туннель обязан жить всё время, пока работает бот.

**Туннель.**

```sh
cloudflared tunnel --protocol http2 --url http://localhost:8090
```

Дождитесь строки `Registered tunnel connection` — без неё туннель не поднялся,
даже если адрес уже выдан. Из вывода возьмите адрес вида
`https://xxxx-yyyy.trycloudflare.com`.

**Бот.**

```sh
set -a && . ./.env.live && set +a
WEBHOOK_URL='https://xxxx-yyyy.trycloudflare.com/webhook' go run ./cmd/bot
```

Адрес туннеля меняется при каждом запуске, поэтому передавать его переменной
перед командой удобнее, чем править файл: она перебивает значение из
`.env.live`. Если всё же правите файл — правьте обязательно. Со старым адресом
бот подпишется на мёртвый туннель, и события пропадут молча: запуск пройдёт
без единой ошибки в логе.

Признак удачного старта — две записи:

```
"msg":"бот зарегистрирован" … "webhook":"https://…/webhook"
"msg":"слушаем события","addr":":8090","path":"/webhook"
```

**Проверка цепочки.** Что туннель действительно доводит запрос до бота, видно
только снаружи — третьим терминалом, пока бот работает:

```sh
set -a && . ./.env.live && set +a          # за секретом подписки

curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://xxxx-yyyy.trycloudflare.com/webhook \
  -H 'Content-Type: application/json' -H "X-Max-Bot-Api-Secret: $WEBHOOK_SECRET" \
  -d '{"update_type":"bot_stopped","timestamp":1,"chat_id":777,"user":{"user_id":42}}'
```

`200` и запись `получено событие` в логе — цепочка «интернет → туннель → бот»
рабочая. Тот же запрос с неверным секретом даёт `401`, и это важно: ответ бота
так отличается от ошибки Cloudflare (`502`, `530`), когда запрос до локального
сервера не дошёл вовсе. `bot_stopped` выбран не случайно — его обработчик
только пишет в лог и не дёргает Max API, так что проверка ничего не отправляет
живым собеседникам.

Останавливают в обратном порядке: `Ctrl+C` боту, потом туннелю. Подписка при
этом остаётся — по умолчанию бот её не снимает (`UNSUBSCRIBE_ON_EXIT`), и
следующий запуск перепишет её на новый адрес.

## Логи

Лог идёт в `stderr` в формате JSON — по объекту на строку. Содержимое переписки
попадает в поле `payload` вложенным объектом, а не строкой с экранированными
кавычками, поэтому запись разбирается одним проходом `jq`.

Записи бывают пяти видов. На одно событие их приходится меньше: у сообщения —
до четырёх (получено, запрос, ответ API, отправлено), у `bot_stopped` — две.

| Запись | Откуда | Что в `payload` |
|---|---|---|
| `получено событие` | `internal/webhook` | тело webhook-запроса ровно таким, каким его прислал MAX — со всеми полями, которых `maxapi.Update` не знает |
| `запрос к API` | `internal/maxapi` | тело `POST /messages` или `POST /answers`; у запросов без тела — `null` |
| `ответ API` | `internal/maxapi` | тело ответа Max, включая тело отказа при `4xx` |
| `ответ отправлен` | `internal/bot` | ничего: только адресат и исход |
| `пользователь остановил бота` | `internal/bot` | без `payload` — только `chat_id` и `user_id`; единственная реакция на `bot_stopped` |

Прочитать, что писали боту:

```sh
go run ./cmd/bot 2>&1 | jq -r 'select(.msg == "получено событие") | .payload.message.body.text'
```

Посмотреть, что ушло в Max:

```sh
go run ./cmd/bot 2>&1 | jq 'select(.msg == "запрос к API") | {path, payload}'
```

Токен в лог не попадает: он уходит заголовком `Authorization`, а заголовки не
логируются вовсе. Секрет подписки в теле `POST /subscriptions` заменяется на
`"***"`.

Размер тела события ограничен 1 МиБ (`webhook.maxBodyBytes`) — тело читается в
память целиком, чтобы попасть в лог неизменным.

## Переменные окружения

| Переменная | Обяз. | По умолчанию | Назначение |
|---|---|---|---|
| `MAX_BOT_TOKEN` | да | — | токен бота; принимается и как `BOT_TOKEN` |
| `WEBHOOK_URL` | да | — | публичный `https://…/путь`, куда MAX шлёт события; `http://` допустим только для петлевого адреса (профиль max-mock) |
| `WEBHOOK_SECRET` | нет | — | секрет подписки, `[A-Za-z0-9_-]{5,256}` |
| `LISTEN_ADDR` | нет | `:8080` | адрес локального HTTP-сервера |
| `MAX_API_CA_FILE` | нет | — | PEM/DER с корневым сертификатом Минцифры |
| `MAX_API_BASE_URL` | нет | `https://platform-api2.max.ru` | подмена адреса API |
| `UNSUBSCRIBE_ON_EXIT` | нет | — | `1` — снять подписку при остановке |

Путь webhook-сервера берётся из `WEBHOOK_URL`: для
`https://example.com/hooks/max` сервер слушает `/hooks/max`.

## Тесты

```sh
go test ./...
go test -race ./...
```

Сеть не нужна: клиент проверяется на `httptest`-заглушке, логика бота — на
подставном `Sender`, webhook — на `httptest.NewRecorder`.

Проверить приём события без туннеля:

```sh
curl -X POST http://localhost:8080/webhook \
  -H 'X-Max-Bot-Api-Secret: dev-secret-123' \
  -H 'Content-Type: application/json' \
  -d '{"update_type":"message_created","timestamp":1,
       "message":{"recipient":{"chat_id":ВАШ_CHAT_ID,"user_id":ВАШ_USER_ID},
                  "body":{"mid":"m1","seq":1,"text":"привет"}}}'
```

## Известные ограничения

Это демонстрационный код. Сознательно не сделано:

- **Нет дедупликации событий.** MAX может доставить событие повторно, если не
  получил быстрый `200 OK`. Бот без состояния, поэтому дубль максимум
  продублирует эхо. В реальном боте нужна проверка по `mid`.
- **Нет повторных попыток при ошибках API.** Сбой отправки только пишется в лог.
  Лимит — 30 rps на домен и 2 сообщения в секунду в один чат; при 429 нужна
  очередь с задержкой.
- **Нет long polling.** `GET /updates` не реализован намеренно: он не годится
  для production и не работает при активной webhook-подписке.
- **Смена одного секрета подписку не обновит.** `GET /subscriptions` секрет не
  возвращает — сверить его не с чем, и `syncSubscription` сравнивает только
  URL и набор типов. Если поменять `WEBHOOK_SECRET`, оставив URL и типы
  прежними, подписка на стороне Max останется со старым секретом, и все
  события начнут отбиваться `401`. Диагностируется по `Warn` «запрос с
  неверным секретом отклонён» в логе; чинится сменой `WEBHOOK_URL` (например,
  добавлением версии в путь) или снятием подписки вручную.
- **Вложения ограничены.** Бот читает `contact` и `location` и отправляет
  `inline_keyboard`; картинки, файлы, стикеры, аудио и видео — ни в ту, ни в
  другую сторону.
- **Привязка номера к аккаунту не проверяется.** Контракт описывает поле `hash`
  вложения `contact` как признак того, что человек поделился номером своего
  аккаунта Max, но алгоритм не публикует — сверить значение не с чем. Бот
  сообщает только о наличии поля.
- **Разбор VCARD упрощён.** Экранирование значений (`\,`, `\;`) не
  разворачивается, параметр в кавычках с двоеточием внутри сломает разбор.
  Контракт таких карточек не порождает. `ENCODING=QUOTED-PRINTABLE` тоже не
  разворачивается — Android в vCard 2.1 обычно кодирует им `FN`, и тогда
  человек увидит `=D0=98=D0=B2=D0=B0=D0=BD` вместо имени, хотя `FN` формально
  не пуст и откат на имя из `max_info` не сработает.
- **`quick` у кнопки геопозиции не используется** — клиент всегда спрашивает
  подтверждение.
- **В логе персональные данные.** Телефон и координаты из вложений пишутся в
  `payload` как есть — ради этого лог и заведён. Для продакшена он в таком виде
  не годится: там нужны маскирование, уровни и ротация.
- **Остановка бота только логируется.** На `bot_stopped` отправить нечего:
  пользователь бота и остановил. Состояния, которое стоило бы почистить, у
  демобота нет.
- **Правка сообщения не перезапускает команду.** На `message_edited` бот
  отвечает эхом правки: показать нужно само событие, иначе оно неотличимо от
  нового сообщения. Правки, сделанные самим ботом, пропускаются — `POST
  /answers` заменяет сообщение с кнопками, и это возвращается как
  `message_edited` с `sender.is_bot`.
- **`bot_added` не воспроизводится на max-mock.** Групповых чатов у эмулятора
  нет, поэтому событие проверяется только на живом Max.
