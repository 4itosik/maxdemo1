# max-mock — эмулятор бот-платформы Max для закрытого контура

Дата: 2026-08-05. Статус: согласован, ожидает ревью перед планом реализации.

## 1. Цель и контекст

Разрабатывается интеграция КЦ-платформы с бот-платформой Max. Разработка и
тестирование идут в закрытом контуре без доступа к реальному
`platform-api2.max.ru`. Нужен эмулятор (далее — мок), который:

- принимает запросы КЦ-платформы по Bot API Max и ведёт себя как реальная
  платформа (stateful: диалоги, сообщения, подписки);
- доставляет webhook-события на зарегистрированные URL стендов;
- даёт тестировщику веб-чат «как мессенджер», чтобы играть роль клиента;
- пригоден для демо заказчику (минимальная правдоподобность переписки);
- **строго соответствует API** — контракт задаётся артефактами этого
  репозитория (`openapi.MaxBotApi.yaml`, `openapi.MaxBotWebhook.yaml`,
  версия 0.0.32).

Не является целью: нагрузочное тестирование, эмуляция искусственных сбоев
(rate limit, 5xx по кнопке), автотесты КЦ в CI (могут появиться позже —
архитектура не мешает).

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Сценарии | Ручное QA + демо заказчику |
| Транспорт событий | Только webhook-подписки (long polling `GET /updates` — вне объёма) |
| Объём API | Текстовый диалог, кнопки/callback, вложения + `/uploads`, правка/удаление сообщений, команды бота. `/chats*` — исключены полностью |
| Сбои | Только честные ошибки API, без искусственных |
| Топология | Несколько ботов, несколько подписок на бота; один мок обслуживает стенды st/ift/dev |
| Хранение | Всё персистентно (SQLite + blob-каталог) |
| Стек | Go (бэкенд), встроенный UI на HTML+vanilla JS, один статический бинарник без npm |
| Авторизация | Обе схемы контракта: `Authorization: Bearer <token>` и `access_token` в query; приоритет у заголовка |
| Код мока | Отдельный репозиторий `maxmoc` (`/Users/aay/endeavors/ailearn/maxmoc`, Go-модуль `maxmock`); спеки берёт из maxapi как версионированный артефакт |
| Тестировщики | Разграничение по боту (URL-закладка `/ui/bots/{botId}`), без логинов |

Важный вывод из анализа спека: **статусов прочтения в Bot API нет** — ни
update-типа, ни поля в `Message` (только `stat.views` для каналов). КЦ не
может узнать через API, что клиент прочитал сообщение. В UI мока «прочитано»
показывается только визуально и никуда не отправляется.

## 3. Архитектура

Один Go-бинарник: статика UI встроена через `embed.FS`, SQLite без cgo
(`modernc.org/sqlite`). В контур переносится один файл (linux/amd64). Пять
компонентов:

1. **Max API-фасад** — HTTP-обработчики на путях реального API (раздел 4).
2. **Ядро состояния** — боты, клиенты, диалоги, сообщения с жизненным
   циклом, подписки, вложения. Форматы идентификаторов повторяют Max
   (`mid.…` для сообщений, int64 для chat/user id).
3. **Диспетчер webhook-ов** — доставка `Update` на подписки (раздел 7).
4. **Control-API + WebSocket** — служебный интерфейс на префиксе `/mock/…`
   (в поверхность Max API не подмешивается): управление ботами и клиентами,
   действия «клиента», журнал, живой стрим для UI (раздел 9).
5. **Встроенный веб-UI** — админка ботов и веб-чат тестировщика (раздел 10).

## 4. Поверхность Max API

Реализуемые операции и их **документированные** коды ответов (сверено с
`reference/max-openapi-official.json`):

| Операция | Коды |
|---|---|
| `GET /me` | 200, 401, 500 |
| `PATCH /me/commands` | 200, 401, 500 |
| `GET /messages` | 200, 401, 403, 500 |
| `POST /messages` | 200, 401, 500 |
| `PUT /messages` | 200, 401, 500 |
| `DELETE /messages` | 200, 401, 403, 500 |
| `GET /messages/{messageId}` | 200, 401, 404, 500 |
| `POST /answers` | 200, 401, 405, 500 |
| `GET /subscriptions` | 200, 401, 500 |
| `POST /subscriptions` | 200, 401, 500 |
| `DELETE /subscriptions` | 200, 401, 500 |
| `POST /uploads` | 200, 401, 500 |

Все прочие пути спека (`/chats*`, `GET /updates`, `GET /videos/{videoToken}`)
отвечают `404` с телом `Error{code: "mock.not_implemented"}`.

## 5. Модель ошибок

Схема `Error` (официальная): `{error?: string, code: string, message: string}`.

- **Документированные ситуации** — ровно по таблице раздела 4: 401 при
  отсутствующем или неверном токене (любым из двух способов), 404 на
  `GET /messages/{messageId}` по неизвестному id, 403/405 там, где заявлены.
- **Недокументированные ситуации** — официальный контракт не содержит 400
  вообще, но реальный Max как-то отвечает на невалидные запросы. Мок
  отвечает **400** с телом `Error`, `code` с явным префиксом `mock.*`:
  - `mock.validation` — тело/параметры не прошли валидацию по OpenAPI;
  - `mock.chat.not_found` — неизвестный `chat_id`/`user_id` в
    `POST /messages`;
  - `mock.callback.not_found` — неизвестный или устаревший `callback_id`
    в `POST /answers`.
  Префикс честно помечает: это конвенция мока, а не знание о проде. При
  появлении доступа к реальному Max наблюдаемые коды вписываются вместо
  `mock.*`.
- Искусственные сбои (принудительные 429/5xx/таймауты) не реализуются.

## 6. Авторизация

Мок принимает **обе** схемы, объявленные в спеке: заголовок
`Authorization: Bearer <token>` (`BearerAuth`) и query-параметр
`access_token` (`ApiKeyAuth`). Приложение, написанное по документации Max,
должно работать против мока без единой правки — сужать этот выбор мок не
вправе. При наличии обоих побеждает заголовок.

Настройка `strict_bearer_auth: true` оставляет только заголовок: она
пригодится, если интеграцию сознательно уводят с токена в URL
(query-параметры оседают в логах прокси и в истории браузера). По умолчанию
выключена.

Токены ботов генерируются моком при регистрации бота в админке.

## 7. События и доставка webhook-ов

Генерируемые события (типы из `models/updates.tsp`, тело исходящего POST —
по контракту `openapi.MaxBotWebhook.yaml`):

| Действие в UI | Update |
|---|---|
| Клиент отправил сообщение (текст/вложение) | `message_created` |
| Клиент нажал инлайн-кнопку | `message_callback` |
| Клиент отредактировал своё сообщение | `message_edited` |
| Клиент удалил своё сообщение | `message_removed` |
| Клиент нажал «Начать» в новом диалоге | `bot_started` |

`bot_started` реализуется как кнопка «Начать» у только что созданного
клиента — как в реальном мессенджере; если КЦ на него не подписана, фильтр
подписки его отсеет.

Семантика доставки:

- на каждое событие POST уходит на **все** подписки бота с учётом фильтра
  `update_types`;
- `SubscriptionRequestBody.url` по спеку требует `https://`, но стенды в
  закрытом контуре живут на `http://`. Мок принимает обе схемы и помечает
  http-подписку в журнале — иначе он неприменим по назначению;
- в рамках одного диалога события доставляются последовательно (порядок
  сохраняется); разные диалоги — параллельно;
- таймаут запроса и 2–3 повтора с экспоненциальным бэкоффом при 5xx или
  сетевой ошибке; каждая попытка фиксируется в журнале;
- несколько стендов работают штатно: каждый регистрирует свой URL через
  `POST /subscriptions` со своим токеном бота.

## 8. Вложения и uploads

Двухфазная загрузка, как в реальном Max:

1. КЦ: `POST /uploads?type=…` → мок возвращает upload-URL, указывающий на
   сам мок (`{base_url}/mock/upload/{token}`). Контрактно URL — непрозрачная
   строка, подмена CDN-адреса законна.
2. КЦ заливает файл (multipart POST) на этот URL → получает токен(ы)
   вложения. Формат ответа upload-эндпоинта в OpenAPI-контракт не входит
   (это CDN-эндпоинт), но однозначно выводится из схем запроса вложения:
   `PhotoAttachmentRequestPayload.photos` — это `Record<PhotoToken>`, а
   `payload` у video/audio/file — `UploadedInfo{token}`. Поэтому мок
   отвечает `{"photos": {"<key>": {"token": "…"}}}` при `type=image` и
   `{"token": "…"}` для остальных типов — ровно то, что примет
   `POST /messages`. Проверяется e2e-тестом (upload → отправка вложения).
3. Токен прикладывается в `POST /messages` (`AttachmentRequest`).

В обратную сторону: файл, выбранный тестировщиком в UI, сохраняется в
blob-каталог мока, а в `message_created` уходит вложение с URL, ведущим на
мок. Blob-ы лежат на диске, в SQLite — метаданные.

## 9. Control-API и WebSocket

Служебный интерфейс на `/mock/api/…` — не пересекается с поверхностью Max
API. Возможности:

- регистрация/список ботов (имя, username, токен);
- создание клиентов (виртуальных пользователей Max: `user_id`, имя), у
  каждого клиента — диалог с ботом;
- действия клиента: отправить текст/файл, нажать кнопку, отредактировать,
  удалить, нажать «Начать»;
- чтение журнала запросов и доставок с фильтрами.

WebSocket `/mock/ws?bot_id=…`: пуш всех изменений состояния в UI в
реальном времени — сообщение бота из `POST /messages`, правка из
`PUT /messages` или `POST /answers`, удаление, результат доставки webhook-а.
Тестировщик видит ответ КЦ в чате мгновенно, без обновления страницы.

**Журнал запросов** — сохраняются все HTTP-обмены в обе стороны:
входящие вызовы Bot API от стендов (метод, путь, тело, статус, латентность,
бот) и исходящие webhook-доставки (тело `Update`, URL подписки, статус
ответа стенда, номер попытки). Это основной инструмент отладки «стенд ↔ мок».

## 10. UI (встроенный, без сборочной цепочки)

Два экрана, оба — статические файлы из `embed.FS` (HTML + vanilla JS, без
npm/React): в закрытый контур переносится ровно один бинарник, сборка UI не
требует ничего, кроме `go build`.

1. **Админка — `/mock`.** Список ботов, регистрация нового бота (выдаётся
   токен), подписки каждого бота, журнал запросов Bot API. Журнал доступен
   и общий (записи подписаны именем бота, неавторизованные — пометкой), и
   в разрезе одного бота — переключателем, с настраиваемой глубиной; для
   каждой записи видны тело запроса и тело ответа. Отсюда переход в чат
   конкретного бота.
2. **Чат — `/mock/chat/{botId}`** (закладка тестировщика). Слева список
   клиентов/диалогов этого бота и кнопка «создать клиента», справа
   переписка: текст, файлы, инлайн-кнопки сообщений бота, правка/удаление
   своих сообщений, кнопка «Начать» в новом диалоге, журнал по этому боту.
   Всё живое по WebSocket. Внешне похоже на окно мессенджера — годится для
   демо. Несколько тестировщиков работают параллельно, каждый со своим
   ботом, не мешая друг другу. Логинов нет (закрытый контур).

React-версия при необходимости добавляется позже отдельным планом: control-API
и WebSocket от UI не зависят.

## 11. Хранение (SQLite)

| Таблица | Содержимое |
|---|---|
| `bots` | id, name, username, token, created_at |
| `clients` | user_id, bot_id, name, username, created_at |
| `dialogs` | chat_id, bot_id, user_id, started (нажат ли «Начать») |
| `messages` | mid, seq, chat_id, sender (bot/client), body (JSON: text, attachments, markup, keyboard), status (active/edited/removed), created_at, edited_at |
| `subscriptions` | id, bot_id, url, update_types, created_at |
| `attachments` | token, type, размер/имя/mime, путь к blob-у |
| `request_log` | ts, direction (in/out), bot_id, method, path, статус, тела запроса/ответа, латентность |
| `webhook_deliveries` | update-тело, subscription_id, попытка, статус, ts |

Всё переживает рестарт. Для `request_log`/`webhook_deliveries` — настраиваемая
ретенция (авточистка записей старше N дней), чтобы долгоживущий сервис не
распухал.

## 12. Соответствие спеку и тестирование

Источник правды — артефакты maxapi: `openapi.MaxBotApi.yaml` (входящие
запросы) и `openapi.MaxBotWebhook.yaml` (исходящие webhook-и).

Кодогенерация **не применяется**: в спеке `NewMessageBody.text/attachments/link`
объявлены `required`, но `nullable`, а `Attachment`/`AttachmentRequest`/
`Button`/`MarkupElement` — дискриминируемые объединения (11/10/8/10 вариантов).
Генератор превращает такие поля в union-типы с `json.RawMessage`, где
различие «поле `null`» и «поля нет» приходится восстанавливать вручную — а
именно оно отличает корректный `PUT /messages` от некорректного. Wire-структуры
пишутся руками (пакет `internal/wire`), а соответствие контракту обеспечивается
валидацией реальных байтов на трёх рубежах:

1. **Входящий запрос** — `kin-openapi` проверяет метод, путь, параметры и тело
   против `openapi.MaxBotApi.yaml`; несоответствие → `400 mock.validation`.
2. **Исходящий ответ** — то же тело ответа валидируется против спека
   (конфиг `validate_responses`, по умолчанию включено). Несоответствие → `500`
   и запись в журнал: это ловит любую ошибку в ручных структурах до того, как
   её увидит КЦ.
3. **Исходящий webhook** — тело `Update` валидируется против
   `openapi.MaxBotWebhook.yaml` перед отправкой; не прошло — не отправляем,
   пишем в журнал доставок как отказ.

Поверх этого — **e2e-тесты полного цикла** (`e2e/`): поднимают мок in-process и
фейковый стенд-webhook, прогоняют сценарий «регистрация бота → подписка →
`bot_started` → сообщение с кнопками → нажатие → `message_callback` →
`answerOnCallback` → правка → удаление → upload и отправка вложения».

Синхронизация: `maxmoc` хранит копии обоих yaml как версионированный артефакт
(версия спека 0.0.32) + make-цель обновления из maxapi. Обновление спека →
расхождения ловят валидация и e2e-тесты мока, а не тесты КЦ.

## 13. Поставка и конфигурация

- Репозиторий `maxmoc`: Go-модуль + `web/` (статика в `embed.FS`).
  `make build` даёт единственный артефакт поставки — бинарник; кросс-сборка
  под контур: `GOOS=linux GOARCH=amd64 make build`. Docker и CI — вне объёма
  текущей итерации.
- Конфиг (yaml + env-переопределения): адрес прослушивания, публичный
  base URL (для генерируемых upload- и attachment-ссылок), путь к SQLite,
  каталог blob-ов, ретенция журнала, параметры доставки webhook-ов
  (таймаут, число повторов).

## 14. Вне объёма

- `/chats*`, `GET /updates` (long polling), `GET /videos/{videoToken}`;
- статусы прочтения через API (в API их нет — только визуально в UI);
- искусственные сбои и chaos-режимы;
- учётки тестировщиков и права доступа в UI;
- групповые чаты (только диалоги «клиент ↔ бот»);
- события `bot_stopped`, `dialog_*`, `user_*`, `chat_*` (диспетчер
  расширяем, добавляются по мере надобности).

## 15. Риски и открытые вопросы

- **Недокументированное поведение реального Max** (коды ошибок вне таблицы
  раздела 4, формат ответов upload-эндпоинта, семантика повторов
  webhook-доставки) — закрыто конвенциями с явной пометкой `mock.*` /
  «по докам»; при появлении доступа к проду сверить и уточнить.
- **`GET /messages` (список)** — реализуется в объёме диалогов
  (фильтр `chat_id`, пагинация по спеку); сценарии КЦ, требующие выборки
  «по всем чатам», не поддерживаются (чатов-групп в моке нет).
- Формат `mid` и диапазоны id подобраны «как у Max» по наблюдениям из
  документации; расхождение формата не ломает контракт (строка остаётся
  строкой), но для правдоподобия желательно сверить при доступе к проду.
